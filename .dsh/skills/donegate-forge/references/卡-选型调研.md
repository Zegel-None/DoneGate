# 卡 · 选型调研

**它回答的问题**：这块砖值不值得接？不接会怎样？调研到什么程度才算够？

## 入口条件

- 已经能写出**缺口句**：缺什么能力、现在靠什么兜、补上以后哪一条判据会从「无法判断」变成有读数。
- 目标技术栈明确（例如「Rust 的 unsafe 块」「iOS 的 UI 流程」「嵌入式的中断优先级」）。
- 手上有候选清单；没有就先按第三节的判据自己搜，不要凭印象报名字。

## 步骤

1. **先把缺口句写下来，写在纸上也不要只放在脑子里。** 句式固定三段：`缺 <能力>；现在靠 <人工/其他工具> 兜；补上后判据 <契约id/判据id> 从 <当前状态> 变成 <能读到什么>`。第三段写不出来，说明这块砖接进来也不会改变任何判定——**停，别接了**。
2. **每条候选标证据档位**，只认三档：
   - **【实测】**：本机真装真跑过，能看到它的真实输出。
   - **【盘上】**：读过它的仓库原文（README、LICENSE、issue、代码结构）。
   - **【声称】**：只看过简介、星数、别人的推荐。
   **标【声称】的候选不许进入选型判定**——这一条是硬的，因为「README 说它做什么」与「它实际输出什么」经常不是一回事。
3. **四件事必须读**，缺一件就退回【声称】档：
   | 读什么 | 为什么必须读 |
   |---|---|
   | **许可证**（LICENSE 原文，不是徽章） | 徽章常与 LICENSE 文件不一致；AGPL/GPL 决定它能不能被集成 |
   | **退出码语义** | 它退 `1` 是「有问题」还是「跑不起来」？两者混用就撞 `INV-10`，必须由砂浆自己归口 |
   | **机器可读输出**（JSON/SARIF/JUnit） | 只能靠人读的文本报告，做不成判据 |
   | **维护活跃度**（最近提交、open issue 数、是否 archived） | 停维护的砖接进来，你替它背锅 |
4. **最多留 3 个候选**。一次评估超过 3 个，比较维度会散掉；超过 5 个必然退化成「谁星多选谁」。
5. **否决也要写理由，而且要可复核。** 一句话 + 一处出处（文件行号、命令、链接）。写不出可复核理由的否决，等于没调研。

## 出口判据

1. 缺口句三段齐，第三段点到具体判据标识。
2. 每个候选都有档位标注，且**进入判定的候选全部是【实测】或【盘上】**。
3. 每个被否决的候选都有一条可复核理由（附出处），不是「感觉不好」。
4. 候选数 ≤ 3。
5. 结论只有三种落点：接（写清 A 还是 B 接法）、不接（写理由）、自写（写两个代价）。
