## 一、先拆成两个正交问题

「长成什么」不是一个问题，是两个：

| 问题 | 内容 | 由谁回答 |
|---|---|---|
| **内核怎么来** | 判据运行、证据记录、状态判定、总账——自己写，还是拼现成工具 | 方案 G |
| **壳选什么** | 这些能力怎么交到使用者（人、Agent、CI）手上 | 方案 A–F |

两者可组合：例如「方案 F 的内核 + 方案 G 的有牙实现」。

## 二、六个壳方案（回答「壳选什么」）

### 方案 A · 纯脚本 + 纪律文件

**形态**：`scripts/` 下的 Node 脚本 + git 钩子 + `AGENTS.md` 纪律条款。没有插件、没有 skill。

| 优势 | 代价 |
|---|---|
| 退出码直接是事实，没有中间层翻译 | 新会话配合与否靠纪律文件自觉，没有机制保证 |
| 人、Agent、CI 用同一组命令 | 判方会话的材料准备要手工 |
| 离开工最近，今天就能开始 | 分发靠 git clone；呈现全靠终端 |

**评审该攻击的点**：纪律文件被忽略时，整个门禁是装饰性的。本仓库现状就是先例——钩子层处于可被 `--no-verify` 绕过的状态。**这个方案的门禁强度等于钩子层的健康度。**

### 方案 B · DSH 插件为壳（四层）

**形态**：脚本原样为第 1 层；插件提供工具表（`status`、树、缺口）、打包 skill（绘制回合、判方自限）、可选呈现层。阻断仍靠脚本与钩子。

| 优势 | 代价 |
|---|---|
| 新会话开箱即用，不依赖先读十份文档 | 插件层随宿主升级而维护 |
| 判方会话用宿主的多会话能力直接开 | **工具输出给模型看，模型可以不复述、可以曲解**——判定不能走这条路 |
| 后续可以长出图形界面 | 分发绑定单一宿主 |

**评审该攻击的点**：插件解决「顺手」，不解决「拦住」。**要攻击的是：插件层会不会让人误以为它在「保证」什么。**

### 方案 C · MCP 服务器

**形态**：核心实现成 MCP 服务器，宿主通过 MCP 调用；其他 MCP 客户端也能用。

| 优势 | 代价 |
|---|---|
| 跨宿主标准化，判方可以用异构客户端 | 多一层协议边界，退出码要在返回值里原样带出并专门核对 |
| 工具 schema 自描述 | 常驻进程与版本管理是新增维护面 |
| | skill 仍要另写；钩子仍要另配 |

**评审该攻击的点**：MCP 不解决任何「防自欺」问题，只解决「跨客户端调用」。**单人单机场景下，为跨宿主付出的复杂度是预付的，可能永远用不上。**

### 方案 D · 纯 skill（说明书流派）

**形态**：全部逻辑写成 SKILL.md 教模型执行：读文件、跑命令、记账、判状态。零代码。

| 优势 | 代价 |
|---|---|
| 最轻，改流程只改文字 | **状态由模型自述，直接违反规格第一条不变量**（INV-01，[02-规格.md](02-规格.md) 第一节：状态只有一个来源） |
| 没有代码要维护 | 判据能不能红，取决于模型是否如实执行 |

**评审该攻击的点**：这套设计存在的理由就是「不由模型自述状态」。**这个方案把第一原则删了，等于产品改姓。** 模型执行纪律不可托管——本包自己的核验脚本就出过「正负样本两套判定」的错（见 ../归档/评审记录/00-五轮评审结论.md（调研/评审材料，不在公开分发包内） 第四节）。**作者倾向否决，列出来是为了让否决有记录。**

### 方案 E · 独立 CLI（npm 包）

**形态**：自成一体、可独立发布的命令行产品；宿主只是「恰好能用终端」的环境之一。

| 优势 | 代价 |
|---|---|
| 不随宿主版本沉浮；人与 CI 直接用 | 判方多会话编排要手工 |
| 版本语义清晰 | 失去宿主原生的工具表与呈现 |
| 面向「任何用 AI 写代码的人」 | 单机单人先付产品化成本（发布、文档站、版本管理） |

**评审该攻击的点**：为想象中的用户付费。**若真实使用者只有作者本人，这个方案的全部包装成本都白付。**

### 方案 F · 内核库 + 多宿主薄壳

**形态**：确定性内核做成独立 npm 库（自带完整测试），外面按需长薄壳——宿主插件壳、CLI 壳、CI 壳。**一个内核，多个壳，壳薄可换。**

| 优势 | 代价 |
|---|---|
| 内核可脱离任何宿主做正负样本测试——本包核验脚本的同款做法照搬到产品 | 前期结构成本最高 |
| 宿主淘汰不伤内核 | 「薄壳纪律」要防逻辑渗进壳里，是一条要长期守的纪律 |
| 与 [adr/002](adr/002-适配器只产声明不产状态.md)（适配器只产声明不产状态）同构——形态本身是设计原则的自举 | 壳的数量必须克制，否则维护面失控 |

**评审该攻击的点**：**现在已知宿主只有一个。先建多壳抽象，是给还没出现的需求付费**；抽象层本身可能变成新的腐化点。

## 三、内核方案（回答「怎么实现」）

### 方案 G · 现成工具组合

**形态**：钩子用 pre-commit / husky；有牙实验直接嵌变异测试工具（Stryker / PIT——业界对照确认过其官方语义：`Detected = killed + timeout`）；总账与功能树用小脚本；呈现用现成面板。

| 优势 | 代价 |
|---|---|
| 最重的一个轮子（变异测试）不用自己造 | **胶水仍要自己写**：冻结记录、运行证据、三方分离、功能树、六栏总账——没有现成工具覆盖 |
| 每件工具都被大量项目锤炼过 | 多工具配置漂移，是新的腐化源 |
| | 变异工具的口径与规格的保守口径（超时不算通过）要先对齐 |

**评审该攻击的点**：看起来省，实际把「一个系统的维护」变成「N 个工具的集成维护」。**设计的核心卖点（证据链、三方分离）恰恰是组合不出来的那部分。**

## 五、作者倾向与不确定

**【评价】以下是推断，不是事实：**

1. **起步选 A。** 理由：A 同时是 F 的内核——**起步 A 不是放弃 F，而是 F 的第一步**。验收实验跑完之前，任何壳都是给未验证的内核做包装。
2. **实验之后在 B 与 F 之间二选一**，决定变量只有一个：**预期使用者是不是只有作者自己的宿主**。是，选 B；想给任何 AI 编码者用，选 F。
3. **D 倾向否决**（违反 INV-01，见上）。
4. **G 与壳方案不互斥**——有牙实验嵌现成变异工具这个决定，可以在 A 阶段就做，不必等形态定案。

**【事实】三件没核实的事，评审前该补：**

| # | 未核实 | 影响 |
|---|---|---|
| 1 | 宿主插件工具层是否原样保留子进程退出码（未按当前插件规范核实） | 若不保真，工具层只能做呈现，不能做判定 |
| 2 | 本仓库钩子层处于可绕过状态（`--no-verify` 可用） | 方案 A/B/C/E/F 的硬门全部悬在它上面 |
| 3 | 判方流程的预期使用频率没有数据 | 决定会话编排层值不值得建 |

## 六、请评审回答的三个问题
