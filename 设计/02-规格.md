## 一、不变量

每条都能机械核对。**任何实现都不许违反，违反即判红。**

| 编号 | 不变量 | 怎么核 |
|---|---|---|
| **INV-01** | 页面上的每个数字只来自判定层，呈现层不许自己统计 | 呈现层的输入只有一个对象；给它两份不同来源的数字，它必须只用一个 |
| **INV-02** | 一个契约的进度只有一种算法：通过与必需之比 | 造一个 3 判据的契约，任何呈现给出的比值必须相同 |
| **INV-03** | 没有任何判据的契约，状态必须是「无法判断」，页面必须写「未定验收」 | 造一个空判据契约，页面不许出现 0/0 |
| **INV-04** | 建目录、写说明、画连线，这三件事不增加任何进度 | 只建目录不写判据，通过数必须仍是 0 |
| **INV-05** | 状态不许由适配器写入 | 适配器契约里没有状态字段；有就判红 |
| **INV-06** | 判据变了而没重签，必须判「无法判断」，不是「过期」 | 改一个判据字符不重签，状态必须是无法判断 |
| **INV-07** | 材料指纹变了必须判「过期」 | 改一行代码不重跑，状态必须变过期 |
| **INV-08** | 没做过有牙实验的判据不计入通过数 | 一条判据跑绿但没做过改坏，通过数不加 |
| **INV-09** | 覆盖率低于 30% 时投影必须拒绝出图，退出码为 1 不是 0；覆盖率在 30%–60% 之间必须出**二档图**（只画已认领部分 + 显式灰区），退出码 0 | 造覆盖率 29% 与 45% 两个仓库，前者 `graph` 必须退 1，后者必须退 0 且图里有灰区 |
| **INV-10** | 退出码 `1`（判定为否）与 `3`（无法判断）不许合并；`2`（确定出事故）不许降级成 `1` 或 `3` | 造三种情形：「跑出来是红的」「命令跑不起来」「还原失败」，三者退出码必须是 1、3、2 |
| **INV-11** | 人工判据必须单独成列，不许混进自动判据的比例 | 页面必须有两个数，不是一个 |
| **INV-12** | 缺口的数量只增不减，不许被任何数字抵消 | 有缺口时总账必须显示缺口数，不许只显示通过数 |
| **INV-13** | `decisions/` 下已存在的文件，在 git 历史里不许出现修改，只许新增 | 对每个已存在文件查 `git log --follow --diff-filter=M`，有结果即红 |
| **INV-14** | `verify pack` 只许含五类：判据原文（含 `assertionId`）、契约的 `scope` 与 `why`、完成声称的原文、`base..head`、运行输出。**只许含这五类，且五类必须齐** | 解开复核包，出现第六类即红，缺任何一类也红；出现「计划」「对话」「思路」字样即红 |
| **INV-15** | 在「过期」状态下改写判据且未重签，状态转为「未验证」，不是「无法判断」 | 造一个过期契约，改判据字符不重签，状态必须是未验证 |
| **INV-16** | 总账六栏（通过、未通过、未验证、过期、无法判断、不稳定）相加必须等于分母；且「通过」一栏必须再拆成**四个**子数（算数 / 无牙 / 未做实验 / 待重验） | 造一条绿红绿的判据，六栏相加必须等于分母；造一条跑绿但没做有牙实验的判据，它必须落在「未做实验」；造一条上游变了没重跑的，必须落在「待重验」 |
| **INV-17** | 每个契约必须挂在至少一个功能上；每个功能必须挂至少一个契约。两者任一为空即 **`orphan`**，进缺口清单 | 造一个没挂功能的契约，`status --tree` 必须把它列进「未登记功能」；造一个没挂契约的功能，必须列进「声明了但没做」 |
| **INV-18** | 每个功能与每条 `after` 连线必须有 `source`（人的原话）。**空值即红，不许用「基于分析」「根据规范」「从代码推断」这类话顶替** | 造一个 `source` 为空的功能，`status --flow` 必须拒绝渲染并报红；造一个 `source` 写「分析得出」的，同样判红 |

## 二、对象字段

七种对象。字段名是实现的契约，逐字使用。**其中「功能」（2.3.1）是后加的第 7 种**，图三与各处的「六种」都以本节为准。

### 2.1 意图 `INTENT.md`

人写的 Markdown，固定四节。

| 节 | 必填 | 验收 |
|---|---|---|
| 为什么做 | 是 | 一句话，不含「更好」「更快」这类没有比较对象的词 |
| 服务谁 | 是 | 写出具体的人或角色，不写「用户」 |
| 什么算成功 | 是 | 至少一条能被外部观察的判据，不写「体验好」 |
| 明确不做什么 | 是 | 至少一条 |

唯一作者是人。每次会话开始必读。不参与上下文压缩。

### 2.2 约束 `CONSTRAINTS.md`

人写的 Markdown。一行一条，格式为「不许 / 必须 + 具体动作」。

| 规则 | 值 |
|---|---|
| 条数上限 | 12。超了要加一条必须先删一条 |
| 每条要能对应一条检查 | 对应不上的单列「只靠人守」，如实显示 |
| 谁改 | 只有人。Agent 起草不算，必须人在提交里确认 |

### 2.3 契约 `contracts/<id>/contract.json`

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | string | 是 | 稳定小写，与目录名一致，定下不改 |
| `title` | string | 是 | 业务语言一句话 |
| `why` | string | 是 | 三行以内。超过三行说明该拆 |
| `scope` | string[] | 是 | 拥有的代码，路径或路径前缀 |
| `obligations` | object[] | 是 | 至少一条，见 2.4 |
| `owner` | string | 是 | 人或角色，不写路径 |
| `dependsOn` | string[] | 否 | 只写契约标识 |
| `provisional` | boolean | 是 | 新建时一律为真 |
| `retired` | object | 否 | `{ date, reason }`。退役不计入任何计数 |
| `overlapsWith` | string[] | 否 | 与谁共享文件。声明了就必须同轮改同轮判 |

### 2.3.1 功能 `functions/<id>.json`（流程图上的一个框）

**一个功能 = 一条成功条件 + 一个机器可验的锚点。** 它是流程图上的一个格子，也是「这个项目有哪些功能」的唯一清单。

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | string | 是 | 稳定标识，如 `booking-crossmidnight` |
| `title` | string | 是 | 一句话，写给人看 |
| `successCriterion` | string | 是 | 对应 `INTENT.md`「什么算成功」里的**原文**，不许改写 |
| `contracts` | string[] | 是 | **挂哪些契约**。至少一个；空数组即「声明了没做」 |
| `after` | string[] | 否 | **流程图上它后面是哪个功能**。**由 Agent 从人的自然语言生成，人不直接编辑这个字段** |
| `source` | string | **是** | **人的原话**：这个框和它后面那条连线，是从哪句话推出来的。**逐字引用，不许改写，不许用「基于分析」「根据规范」「从代码推断」顶替**。空即红（INV-18） |
| `note` | string | 否 | 这个框为什么存在 |

**人只说，不说结构化数据。**

| 元素 | 谁产生 | 人怎么参与 |
|---|---|---|
| `id` / `title` | Agent | 说「我要有个预约流程」 |
| `after` 横向连线 | **Agent 从自然语言生成** | **顺口说出来**，不画 |
| `contracts` 纵向锚点 | Agent 起草，人确认 | 说「这个框对应 booking-create」 |
| 节点状态 | 机器算 | 不参与 |
| `source` 原话引用 | **Agent 逐字摘录** | 不参与，但**可以核对** |

**人唯一要动手的事，是看图并说「不对」。** 结构化数据全部由 Agent 产出。

**`successCriterion` 必须是 `INTENT.md` 的原文，不许改写。** 改写了就成了一份独立清单，会和意图分叉。**一个事实一个家。**

**功能树与流程图是同一批节点的两种连线**：

| 视图 | 连线 | 谁给 |
|---|---|---|
| **功能树**（`status --tree`） | 纵向归属：功能 → 契约 → 判据 | 机器（从 `contracts` 与 `scope` 算） |
| **流程图**（`status --flow`） | 横向顺序：功能 → 功能 | **人（`after` 字段）** |

**两个视图的节点完全相同，状态完全相同，只有连线不同。** 所以不存在「两份清单对不上」的问题——只有一份节点清单，两份连线。

### 2.4 判据

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `id` | string | 是 | 契约内唯一 |
| `kind` | `"command"` \| `"human"` | 是 | 只有两种 |
| `command` | string | 当 kind=command | 单条命令，不许串联、不许带管道落盘 |
| `expect` | object | 是 | `{ exitCode, stdoutMatches? }` 或 human 的一句判断标准 |
| `frozenHash` | string | 是 | 判据内容的哈希 |
| `signedBy` | string | 是 | 空着 = 未冻结，门 2 不过 |
| `required` | boolean | 是 | 为真才进分母 |
| `teeth` | object | 否 | `{ at, tier, result }`。没做过就没有这个字段 |
| `breakPatch` | object | 否 | `{ file, line, from, to }`。有牙实验档 A 用 |
| `timeoutSec` | number | 否 | 覆盖默认 600 秒 |
| `inputClasses` | string[] | 是 | 至少一项，取值 `正常`/`边界`/`异常`。门 2.4 要求本契约三类各有（判法见 §15.1、§15.2） |
| `spansContracts` | string[] | 否 | 这条判据跑的是哪几个契约的代码，跨契约集成判据用它 |
| `servesSuccessCriterion` | string | 是 | 服务意图里的哪一条成功条件 |

### 2.5 决策记录 `decisions/<日期>-<短名>.md`

固定五段：当时的问题、可选方案、选了哪个、为什么、什么条件下翻案。

| 规则 | 值 |
|---|---|
| 何时写 | 只在改了判据、改了契约边界、改了意图时写 |
| 可否改写 | 不可。只能被新记录取代，取代关系写在新记录里 |
| 谁的 | 人写。Agent 可以起草，必须人确认 |

### 2.6 证据 `.node-contract/evidence/<契约>/<判据>/<时间戳>/`

三份文件，缺一份就不算一次有效运行。

| 文件 | 何时写 | 必含 |
|---|---|---|
| `start.json` | 运行前 | 契约、判据、命令原文、材料指纹、开始时间、运行器版本 |
| `report.json` | 运行后 | 退出码、输出摘要、实测值、耗时、是否超时 |
| `end.json` | 收尾 | 成功或失败、三份文件的相互哈希 |

**三份之间的互相哈希**：`report` 含 `start` 的哈希，`end` 含 `report` 的哈希。断任何一环，整份证据判「无法判断」。

## 三、计数规则

补的是「一个契约多条判据时分母怎么算」。

### 3.1 分母

| 情况 | 计入分母 | 说明 |
|---|---|---|
| `required: true` 且 `kind: command` | 是 | 主分母 |
| `required: true` 且 `kind: human` | 是，但**单独一列** | 页面必须显示两个比值 |
| `required: false` | 否 | 只显示，不计数 |
| 一条判据有多个检查点 | 算**一条** | 内部全过才算这条通过 |
| 退役契约里的判据 | 否 | 整个契约不进任何计数 |

### 3.2 「通过」的定义

只认**最近一次运行**，不要求连续 N 次。

但有一条附加标记：同一判据**连续三次结果不同**，标「不稳定」，并进缺口清单。不稳定不算通过也不算不通过，它单独一类。

### 3.3 契约级状态

取最差的那一档，优先级从差到好：

```text
无法判断 > 未通过 > 过期 > 未验证 > 通过
```

一条判据未通过，不改其他判据的状态，只让契约级的通过比下降、契约级状态取到「未通过」。

### 3.3.1 功能层两个计数

**它们是「这个项目有哪些功能」这个问题的答案。** 没有这两个数，功能清单会与实现悄悄分叉。

| 计数 | 定义 | 怎么算 | 页面显示 |
|---|---|---|---|
| **孤儿功能** | 声明了要做，但没有契约实现 | `functions[].contracts` 为空，或全部指向不存在的契约 | 「声明了但没做」，进缺口清单 |
| **孤儿契约** | 有契约，但没有功能挂它 | 某个契约的 `id` 不出现在任何 `functions[].contracts` 里 | 「做了但没登记是哪个功能」，**必须列清单，不许自动归** |

**孤儿契约是这三个数里最重要的一个。** 它抓的是「你干了活，但没人记得这算个功能」——**这正是项目变大以后开发者自己都忘了有哪些功能的那个缺口。**

**不许自动归**：机器能发现「这个契约没挂功能」，**但不能替你决定它该挂哪个功能**。自动归等于把「这算什么功能」这个判断偷偷交给机器，与 [adr/005](adr/005-删掉代码按业务流程组织这条前提.md) 撤掉的那个前提是同一个坑。

**两个数都要进总账**，与 §3.4 的六栏并列，不混淆：

```text
功能 12 项：有实现 9、孤儿功能 2、孤儿契约 1
```

### 3.4 一句总账

格式固定，逐字：

```text
本轮 N 项：通过 A、未通过 C、未验证 D、过期 E、无法判断 F、不稳定 G
其中通过里：算数 A1、无牙 A2、未做实验 A3、待重验 A4
```

**六栏相加等于分母**：`A + C + D + E + F + G = N`。不等就是错（INV-16）。**分母 `N` 只数进分母的义务，`teeth = ignored` 的不在其中。**

**「通过 A」与「通过数」是两个名字、两个数，不许混用**（这一条是为了堵住规格里同名两义的口子）：

| 名字 | 等于什么 | 说的是 | 谁在引它 |
|---|---|---|---|
| **通过 A** | `A1 + A2 + A3 + A4` | **状态计数**：这么多判据跑绿了 | 六栏总账的第一栏 |
| **通过数** | **只等于 `A1`（算数）** | **可信计数**：这么多判据的绿值值得信 | INV-08「没做过有牙实验不计入通过数」、§3.5 定案 B「通过数计 1」 |

**「待重验」（A4）因此有两个身份，别读混**：它是「通过 A」的一个子数（所以算在六栏第一栏里、六栏相加仍等于分母），但它**不是「通过数」**（§11.1 说它不计入通过数，指的就是这个）。两个说法都对，只要认清说的是哪一个。

**「通过」不再是一个数，是四个数**，加起来才是 A。**下面这张表是唯一权威定义**——脚本、页面、任何实现都必须由它派生，不许各写一份谓词。

#### 3.4.1 四个子数的判定表

**必须按行从上往下匹配，第一条命中即止。这个顺序本身就是规则的一部分。**

> **本表的机器可读权威是 [`../tools/classification.json`](../tools/classification.json)。** 下面这张表是它的渲染结果；改条件请改那个 JSON，不要改这张表或脚本。`tools/verify-spec.mjs` 直接读它驱动分类器，并逐行核对本表是否与它一致——**只改条件不改名称也会判红**（已用「把 A1 的 `killed` 改成 `survived`」验证过：会报条件不一致 + 重叠 + 遗漏三条）。

| 序 | 条件 | 归入 |
|---|---|---|
| **1** | `run = pass` **且** `pendingRecheck = true` | **`A4` 待重验** |
| **2** | `run = pass` **且** `pendingRecheck = false` **且** `teeth = killed` | **`A1` 算数** |
| **3** | `run = pass` **且** `pendingRecheck = false` **且** `teeth ∈ {survived, no-coverage, compile-error, runtime-error, timeout, red-wrong-assertion, hollow-assertion}` | **`A2` 无牙** |
| **4** | `run = pass` **且** `pendingRecheck = false` **且** `teeth = undefined` | **`A3` 未做实验** |
| — | `run ≠ pass` | **不在这四栏**，走「未通过」或「无法判断」 |
| — | `teeth = ignored` | **不在这四栏，也不进分母**，页面单列「已忽略的判据」（§6.1） |
| — | 以上都不匹配 | **判红**（出现规格没定义的状态组合） |

**三条硬要求**：

1. **互斥**：任何义务不得同时命中两行。
2. **穷尽（限「进分母的通过子集」）**：`run = pass` 且 `teeth ≠ ignored` 的义务必须恰好命中一行。**`teeth = ignored` 的不进分母**，它走下面那条单列规则，所以不受四行穷尽约束。
3. **表是唯一权威**：脚本不许另写谓词。要么解析这张表，要么把这张表逐行抄成数据结构，并在脚本里注明「抄自规格 §3.4.1」。**抄写与规格不一致时以规格为准，且脚本判红。**

#### 3.4.2 上一版为什么不行

上一版四个谓词**分开写、没规定优先级**，复审用独立判定器逐个验出三处重叠或遗漏：

| 组合 | 上一版 | 判定表 |
|---|---|---|
| `pass` + `survived` + `pending` | A2 与 A4 同时命中 | **A4**（第 1 行优先） |
| `pass` + 无实验 + `pending` | A3 与 A4 同时命中 | **A4**（同上） |
| `pass` + `compile-error` + 不 pending | 无一命中（A2 枚举漏了它） | **A2**（第 3 行枚举已补全） |

**根因不是「漏了几个状态」，是「没有规定优先级」。** 四个谓词各写各的，重叠处靠实现者猜，遗漏处靠运气。

**为什么要把「通过」拆开**：上一版写的是「通过 A（其中 B 项有牙）」，读者会把 A 当成「算数的通过」，而它其实是「跑绿的通过」——**这两个数在决策上完全不同**：前者说「这么多判据可信」，后者说「这么多判据跑过了，其中一部分不可信」。§3.5 定案 B 已经把「状态」与「算不算数」分开，总账格式必须同步。

**「不稳定」为什么单独一栏而不是塞进「通过」或「未通过」**：绿红绿是同一判据的多次运行，它既不是稳定的通过也不是稳定的失败。塞进任何一边都会掩盖「这条判据本身不可靠」这个信息。**但它占分母**——因为这条判据确实要人去看。

### 3.5 三处状态冲突的定案

外部审计指出三处规则互相冲突。定案如下，**实现时以这张表为准**：

| 输入 | 图上怎么说 | 不变量怎么说 | **定案** | **依据** |
|---|---|---|---|---|
| 在「过期」状态下改写判据且未重签 | 回到「未验证」 | INV-06 要求「无法判断」 | **未验证** | 见下 A |
| 两条必需判据都跑绿，仅一条做过有牙实验 | 走查显示通过 2/2 | INV-08 最多计 1/2 | **通过数计 1，两个状态都是「通过」** | 见下 B |
| 必需判据连续出现绿、红、绿 | §3.2 单列「不稳定」 | §3.4 要求**六栏**相加等于分母（含不稳定） | **不稳定独立成第六栏，占分母** | 见下 C |

#### A · 为什么「未验证」而不是「无法判断」

**「无法判断」的定义必须收窄，否则它会变成逃生舱。** 这一点有现成的论证：三值逻辑里那个「不确定」值，只有在**契约明确规定了它适用边界**时才有意义，否则它就退化成「我不想回答」。

> 参考：三值契约的讨论里指出，「indeterminate」的正当性完全来自契约——契约划定了「真正不可判定」与「只是不希望」之间的界限；抽掉契约，第三个值就退化为自由裁量。

所以本设计把「无法判断」的**唯一适用条件**写死：

| 能用「无法判断」的情形 | 不能用「无法判断」的情形 |
|---|---|
| 判据命令跑不起来（`runtime-error`） | 跑起来了但结果是失败 |
| 材料读不出来（文件缺失、权限不足） | 材料读得出来但内容变了 |
| 判方必需的材料不全（`材料不足`） | 判方看得到但不同意 |
| 指纹算法坏了（H3） | 指纹对不上（那是新鲜度，走过期） |

**「改了判据但没重签」不属于上表左列**：材料读得出来，只是旧结论不适用。所以是「未验证」——**新判据还没跑过，不能算通过；但也不是「判断不了」，因为重跑一次就能判断。**

#### B · 为什么「通过数」与「状态」要分开计

这两个是不同的问题：

| 问题 | 答案归谁 |
|---|---|
| 这条判据**跑绿了吗** | 状态（五个词之一） |
| 这条判据**的绿值不值得信** | 通过数（只算有牙的） |

**把它们合成一个数字就是审计批评的「运行事实、证据适用性、验收决定混在一个状态里」。** 本轮不拆三个维度（那是重构），但至少在这一点上分开：状态说「跑绿了」，通过数说「其中几条算数」。

#### C · 为什么「不稳定」单列而不塞进五个状态

塞进去会破坏两条更重要的性质：

1. **六栏相加等于分母**（§3.4，INV-16）。绿红绿是**同一个判据的多次运行**，它独立成第六栏，占一个分母位置——状态栏里它既不是通过也不是未通过。
2. **「不稳定」本身是一条缺口信号**，要进缺口清单、要人看。塞进「未通过」会让它混在一堆真实失败里，塞进「未验证」会让人以为重跑就好。

所以：**`不稳定` 独立成第六栏，总账必须显示六栏之和 = 分母**（INV-16）。**它不是「五状态之外的附注」，是一个占分母的独立栏**——因为它确实要人去看。

## 四、判据执行规格

补的是「命令怎么跑」。

**先说清这一节能保证什么、不能保证什么。**

| 这一节能保证的 | 这一节**不能**保证的 |
|---|---|
| 约定运行器该做什么 | **它不能把普通子进程变成沙箱** |
| 记录它实际做了什么（声明 + 探针） | 它自己不做系统调用过滤 |

**上一版写的是「这一节是安全边界」，那句话是错的。** 外部审计指出：「仅设项目根工作目录和环境变量白名单，普通子进程仍可按自身权限访问其他路径。」**这是事实**——一个普通 `node` 进程想读 `/etc/passwd` 就读得到，想连外网就连得上。

**真正的隔离要靠操作系统机制，本设计不重造它们**：

| 手段 | 做什么 | 出处 |
|---|---|---|
| `seccomp` | 限制可用系统调用集 | Linux |
| `landlock` | 无特权文件系统访问控制 | Linux 5.13+ |
| `namespaces` | 隔离挂载、PID、网络 | Linux |
| `nsjail` / `bubblewrap` | 把上面几个封好的现成沙箱 | 开源 |
| **hermetic execution** | 动作不许访问未声明输入 | Bazel 的做法 |

**所以本设计改成三段式**：

| 段 | 谁做 | 做什么 |
|---|---|---|
| **声明** | 运行器 | 在 `runner.json` 里写清它用了哪种隔离（`seccomp` / `landlock` / `nsjail` / `none`），以及隔离了哪些维度（文件 / 网络 / 进程 / 环境） |
| **记录** | 运行器 | 每次执行把「实际生效的隔离」写进证据，和声明不一致即红 |
| **验收** | 门 4 | 跑两条探针，**两条都必须失败**，否则运行器不合格 |

**两条探针**：

| 探针 | 命令 | 期望 | 不期望意味着 |
|---|---|---|---|
| 越界读 | 读项目根之外的一个文件（如 `/etc/hostname`） | **失败**（权限拒绝） | 文件系统没隔离 |
| 越界连 | 连一个外网地址 | **失败**（连接拒绝） | 网络没隔离 |

**`isolation: none` 是允许的，但必须显式声明**，且页面要在每条证据旁标注「本次运行无隔离」。**允许声明不代表允许假装**：声明 `none` 却声称安全，比不声明更糟。

| 项 | 规定 | 为什么 |
|---|---|---|
| 工作目录 | 项目根。不许由判据自己改 | 改目录等于让判据访问项目之外 |
| 超时 | 默认 600 秒，可由 `timeoutSec` 覆盖 | 死循环必须被杀 |
| 超时处置 | 杀整棵进程树，判「无法判断」，退出码 **3** | 只杀父进程会留下孤儿 |
| 输出上限 | 262144 字符。超限杀进程树，判「无法判断」 | 无限输出会吃满内存 |
| 环境变量 | 白名单。默认只给 `PATH`、`HOME`、`LANG` | 判据不该看到密钥 |
| 网络 | 默认禁。要联网必须显式标注 `needsNetwork: true`，并在页面单列 | 联网判据不可复现 |
| 并发 | **串行**，一条一条跑 | 并发会互相踩，实测并发八路时 71% 误红 |
| 退出码 | 直读子进程退出码，不经任何包装层 | 包装层会把它自己的码替换成判据的码，判据变装饰 |
| 写入 | 判据只许写自己的证据目录与临时目录。**这一条要靠上面说的文件系统隔离来落实，运行器自己无法保证** | 防止判据改别的契约的文件 |

**三条禁令**（命中即判红，不是警告）：

1. 判据命令里出现 `|| true`、`; exit 0`、`--no-fail` 这类吞失败的写法。
2. 判据命令经包管理器包装执行（会吞退出码）。
3. 判据命令改测试文件、改判据文件、改约束文件。

## 五、总线记录格式

补的是「适配器产出什么」。**适配器只许填这九个字段，多一个都不许。**

| 字段 | 类型 | 必填 | 含义 | 校验 |
|---|---|---|---|---|
| `stage` | 1–7 | 是 | 服务哪个阶段 | 一个适配器只服务一个阶段 |
| `tool` | string | 是 | 哪家工具 | 必须在已注册清单里 |
| `version` | string | 是 | 工具版本 | 变了导致输出变化时，受影响判据判「过期」 |
| `role` | `hard` \| `soft` | 是 | 硬：产出能进门禁。软：只给人读 | 软适配器缺失不影响门禁，硬缺失必须降级 |
| `inputs` | object[] | 是 | 吃了什么，每项带路径与哈希 | 少一项就没有指纹 |
| `artifacts` | object[] | 是 | 吐了什么，每项 `{ path, sha256, kind }` | 文件必须真实存在 |
| `claims` | object[] | 是 | 声称做成了什么，每条 `{ text, checkedBy }` | `checkedBy` 必须指向一条真实判据，指不上就进缺口 |
| `unresolved` | object[] | 是 | 没解决什么，每条 `{ text, stage }` | `stage` 必须是七阶段之一，不许写「以后」 |
| `degradedTo` | string | 是 | 这个工具缺席时退化成什么 | 不许是「跳过」，只许是「人工按同一格式手写」 |

**总线自己的字段**（记录元信息，不归适配器填）：`id`、`at`、`durationMs`、`fingerprint`、`accepted`。

**INV-05 的落点**：这张表里没有状态字段，也没有能让状态被推断出来的字段。适配器说「我生成了三个文件、声称澄清了 12 条、有 3 条没澄清」，状态由门禁读了文件和证据之后自己算。

**`claims.checkedBy` 的用法**：每条声明必须挂在一条判据上。挂不上，说明这条声明无法核对，进缺口。这是防「适配器自称做完了」的唯一办法。

## 六、有牙实验三档

补的是「改坏什么」。按项目能力选一档，**用了哪一档必须在页面标出，因为不同档的「有牙」不是同一件事。**

| 档 | 名字 | 怎么改坏 | 成本 | 覆盖面 |
|---|---|---|---|---|
| **A** | 手写改坏 | 读判据的 `breakPatch`：改哪个文件、哪一行、从什么改成什么 | 每条判据要人写一次 | 全语言 |
| **B** | 变异算子 | 接 StrykerJS 这类工具，用它的算子集自动改 | 低 | 只覆盖它支持的语法 |
| **C** | 回滚真实故障 | 从 git 历史找一条真实 bug 修复，回滚掉 | 最高 | 最贴近真实 |

**默认档 A。**

### 6.1 实验流程（三档共用）

**这一节用的是变异测试（mutation testing）的成熟做法，不是自创。** 术语与状态词汇直接取 PIT 与 Stryker 的公开定义，理由见 [adr/014](adr/014-用领域成熟词汇而不是自创词汇.md)。

1. 记录被测实现文件的哈希，以及**判据将要触发的断言**（见下面的 `assertionId`）。
2. 按档改坏。
3. 跑判据，按下表给这次改坏**定一个状态**。
4. 还原，核对哈希与第 1 步一致（不一致就是 `restore-failed`，退出码 2）。
5. 再跑判据，要求它 `passed`。
6. 结果写进 `teeth`，状态用下表的值。

**变异体状态表**（取自 PIT 的 `DetectionStatus` 与 Stryker 的 mutant states）：

| 状态 | 定义 | 算「有牙」吗 | 依据 |
|---|---|---|---|
| `killed` | 改坏后**至少一条断言失败**，且失败的是目标断言 | **算** | PIT `KILLED`、Stryker `Killed` |
| `survived` | 改坏后所有断言都通过 | **不算** | PIT `SURVIVED`、Stryker `Survived` |
| `no-coverage` | 改坏的那一行**根本没有判据执行到** | **不算，且比 `survived` 更差** | Stryker 原文：「a survivor (worse than Survived)」 |
| `compile-error` | 改坏后代码编译／加载不起来 | **不算，且不作任何证据** | Stryker 把 `CompileError` 归为「生成变异体时自身的失败」，不是关于测试的证据 |
| `runtime-error` | 改坏后运行时崩了，不是断言失败 | **不算，且不作任何证据** | 同上，Stryker `RuntimeError` |
| `timeout` | 改坏后跑不完 | **不算，单列**（**这是本项目的保守选择，不是业界共识**） | Stryker 官方把 Timeout **计入 detected**，见下 |
| `red-wrong-assertion` | 失败的不是目标断言 | **不算** | 本设计新增，补 `compile-error` 管不到的情形 |
| `restore-failed` | 还原后哈希不一致 | **不算，退出码 2** | 本设计原有规则 |

**`timeout`：上一版把 Stryker 的说法写反了，这里更正。**

| 来源 | 原文 | 结论 |
|---|---|---|
| **Stryker 官方**（[Mutant states](https://stryker-mutator.io/docs/mutation-testing-elements/mutant-states-and-metrics/)） | 「**It is counted as "detected"**. The logic here is that if this mutant were to be injected in your code, your CI build would detect it because the tests will never complete.」 | **Timeout 计入 detected** |
| Stryker 的指标定义 | `Detected = killed + timeout` | 同上 |
| PIT `DetectionStatus` | `TIMED_OUT(true)` | 同上 |

**上一版写的「Stryker 说 Timeout 是 inconclusive, not a survivor」是错的。** 那句话来自某个第三方 crate 的注释，被当成了 Stryker 官方定义。**这是引用链没查到底的错误**，不是判断分歧。

**本项目的选择**：`timeout` 单列，**不计入有牙**。

**理由是保守，不是业界如此**：在单人项目的验收语境里，一条判据超时可能有两种原因——它抓到了死循环（那是有牙），或者它自己太慢（那是判据的问题）。**这两种在证据上分不开**，所以本项目选择不计。

**但必须标明这是本项目策略**：任何读到这一节的人都应该知道，Stryker 与 PIT 都算 detected，**只有本设计不算**。这不影响内部一致性，但影响「我引用业界做法」这句话的成立范围。

**顺带补两个上一版漏掉的状态**（Stryker 有八个，我只搬了六个）：

| 状态 | Stryker 的定义 | 本设计怎么处理 |
|---|---|---|
| `pending` | 已生成但还没跑 | 本设计里不会出现（有牙实验是一次性同步的），出现即按「未知状态」判红 |
| `ignored` | 被用户显式忽略，不计入分数但出现在报告里 | 本设计允许 `teeth.ignored`，**但必须在页面单列「已忽略的判据」**，且它们不计入通过数 |

#### `teeth` 的全部合法取值（唯一清单）

**上一版没有这份清单**：§3.4.1 的 A2 行枚举 7 个、本节主表 8 个、补充表 2 个，三处各写各的，实现者按哪一份都能自证正确。**下面这张表是唯一出处**，`tools/classification.json` 的 A2 枚举必须是它的子集。

| 值 | 类别 | 算「有牙」吗 | 出处 |
|---|---|---|---|
| `killed` | 变异体状态 | 算 | PIT / Stryker |
| `survived` | 变异体状态 | 不算 | PIT / Stryker |
| `no-coverage` | 变异体状态 | 不算 | Stryker |
| `compile-error` | 变异体状态 | 不算，不作证据 | Stryker |
| `runtime-error` | 变异体状态 | 不算，不作证据 | Stryker |
| `timeout` | 变异体状态 | 不算（本项目保守选择） | 见上文 |
| `red-wrong-assertion` | 变异体状态 | 不算 | 本设计新增 |
| `restore-failed` | 变异体状态 | 不算，退出码 2 | 本设计原有 |
| `pending` | 变异体状态 | 出现即判红（本设计不允许） | Stryker |
| `ignored` | 变异体状态 | 不算，页面单列 | Stryker |
| `hollow-assertion` | **判据质量状态，不是变异体状态** | 不算 | 本设计原有；与变异体无关，只因为它也是 `teeth` 的取值才并列在这里 |

**两套词汇必须分清**：变异体状态说的是「这次改坏尝试出了什么结果」，`hollow-assertion` 说的是「这条判据本身守不住东西」。它们共用 `teeth` 一个字段，所以必须在一张表里清点，但**不许互相顶替**——尤其是不能用「反正是 hollow 所以不用做改坏实验」当理由省略门 3。

#### 两条从业界直接搬来的硬规则

**规则一：未知状态一律判失败，不许默认通过。**

> 来自 `llm-code-execution` 的 `mutation-decide.mjs`：「AN UNKNOWN STATUS IS A FAILURE, never a pass. This file hard-codes a status vocabulary; if Stryker adds one, the gate must stop rather than silently treat it as acceptable.」

落地：`teeth` 读到不在上表里的状态值，**退出码必须是 `3`（UNKNOWN）**，不是 0，也不是 2。**理由**：我们不认识这个词，说明**判断不了**，不是「确定出了问题」。它同样不许算作通过——`3` 与「通过」的区别就在这里。

**规则二：判据必须能被一个现实的 bug 证伪。**

> 来自 CRUCIBLE 的 test-quality 方法：「Each assertion must be FALSIFIABLE by a realistic bug.」

这条比「判据必须能红」严格：能红可能只是被语法错误弄红的。**能红 + 红在目标断言 + 目标断言对应一个现实会发生的缺陷**，三条都成立才叫有牙。

#### `assertionId`、被验证命题、空心断言

**上一版把六种语法模式（`is not None` / `.exists()` / `assert True` / `len >= 0` / `len >= 1` / `isinstance`）一律判成空心断言、一律不计入有牙。复审指出这是错的：这些写法是不是空心，取决于它对应的承诺是什么。**

**对的是这一点**：

| 被验证的承诺 | 合适的证据 | 不能据此扩大的结论 |
|---|---|---|
| 「导出动作创建了指定文件」 | 检查文件存在；**删掉创建动作应使断言失败** | 文件内容符合业务要求 |
| 「查询至少返回一条可用记录」 | 非空 **加上**「可用」的必要属性检查 | 全部查询条件都正确 |
| 「目录下有 8 份检查脚本」 | 明确文件集合后计数 | 这些脚本有效、内容正确，或内容未变 |
| 「文件内容与冻结版本一致」 | 内容哈希匹配 | 冻结版本本身正确 |

**所以 `assert x is not None` 既可能是合格的（当承诺就是「字段被填了」），也可能是空心的（当承诺是「金额正确」）。判据是承诺，不是语法。**

**改法：判据必须声明三件套。**

| 字段 | 内容 | 例子 |
|---|---|---|
| `claim` | 这条判据承诺什么（一句话，**必须是一个可被现实 bug 打破的命题**） | 「导出 2026-11 的账单时，金额等于该月预约总额」 |
| `observable` | 用什么观察它（断言写在哪个具体值上） | `assert total === 123400`（分） |
| `scope` | 这个结论**不**覆盖什么 | 不覆盖跨月预约、不覆盖折扣 |

**语法扫描降级为提示，不再作门禁**：

| 上一版 | 现在 |
|---|---|
| 六种语法模式命中 → `hollow-assertion`，不计入通过数 | 命中 → 页面标「**疑似空心，请确认 `claim` 是否对应它**」，**不作门禁判定** |
| 由机器判定空心 | **由 `claim` 与 `observable` 的对齐判断**，机器只提示，人确认 |

**`assertionId` 仍然保留**，但它指向的是 `claim` 的标识，不是一条断言的语法位置。

**为什么这样改**：上一版的做法是「用语法特征代理命题有效性」——**这正是本设计 [adr/013](adr/013-代理量必须与它代理的东西同向.md) 禁止的事，我第三次犯。** 语法特征与命题有效性不同向：同一个 `is not None` 在两种承诺下有效性相反。

**代价**：判据写起来更重（要写三件套），且「疑似空心」的提示需要人看。**但这个代价换来的是「规则满足 ≠ 证明的是另一件事」这个毛病被从源头堵住**——这正是复审第四条的要求。

**一个必须能复现的反例**（用它验收这一节）：正确返回 42 的价格函数，判据只断言「能加载并返回数字」。

| 改动 | 判据 | 状态 | 该不该算有牙 |
|---|---|---|---|
| 42 → 语法错误 | 红 | `compile-error` | 不算（不作证据） |
| 42 → 0（合法业务错误） | **绿** | `survived` | 不算 |
| 判据本身 | — | `hollow-assertion` | 不算（它守不住任何值） |

### 6.2 四条硬规则

1. **第 4 步哈希不一致，退出码必须是 2，不是 1。** 还原失败意味着仓库现在处于被改坏的状态，是事故，不是判定结果。
2. **第 5 步跑不绿，说明判据不稳定**，这条判据不许标有牙，标「不稳定」。
3. **档 B 的实验结果不许与档 A 混算。** 页面必须分开显示「手写改坏的有牙率」与「算子改坏的有牙率」。
4. **判据必须声明它守哪条承诺**（`claim` 与 `observable`），且两者要能对上。**不许用语法模式判空心**——语法扫描只作提示、不作门禁（见 6.1）。这一条是 6.1 第 3 步能执行的前提。

## 七、判方 rubric

补的是「判方凭什么判」。五项，每项只能答 `pass` / `fail` / `unknown`（判定规则见 7.1）。

| # | 项 | 判什么（**五项都是「满足才是好结果」**） |
|---|---|---|
| **V1** | 范围 | 改动**全部**落在契约声明的 `scope` 内 |
| **V2** | 可定位 | 每条判据都能定位到改动里的**具体位置**，不是「应该有关」 |
| **V3** | 无放水 | **未发现**无正当理由的判据放宽（放宽断言、删用例、改容差、加跳过）。例外见 7.2 |
| **V4** | 无未覆盖 | **未发现**明显会被这次改动破坏、而判据没覆盖到的行为 |
| **V5** | 无越界 | **未发现**超出判据实际证明范围的声称 |

**每项只答三个值**：`pass` / `fail` / `unknown`。

> **上一版把 V3、V4、V5 写成反向命题**（「有没有放水 / 有没有漏 / 有没有越界」），再用「反向项答违反才算过」去补。**复审指出这与「任一项违反就不过」直接冲突**：同一份干净改动，按第一条判不过，按第二条判通过。
>
> **改法是消除方向本身**：五项全部写成「满足才是好结果」的正向命题，判定规则只剩一条，不再需要「正向项」「反向项」这对概念。

### 7.1 判定规则

| 五项的结果 | 门 5 | 退出码 |
|---|---|---|
| 五项全 `pass` | **通过** | 0 |
| 任一项 `fail` | **不过**（有问题） | 1 |
| 无 `fail`，但至少一项 `unknown` | **不过**（材料不足） | 3 |

**`fail` 与 `unknown` 必须分开**：前者说「查到了问题」，后者说「材料不够，判断不了」。压成一个「不过」会让人分不清下一步该改代码还是该补材料。

**`unknown` 是信息，不是免责**：它必须写进缺口清单。而且不能用来搁置不方便的结论——见 7.3。

### 7.1.1 一张对照表

| 改动 | V1 | V2 | V3 | V4 | V5 | 结论 |
|---|---|---|---|---|---|---|
| 干净改动 | pass | pass | pass | pass | pass | **通过** |
| 放宽了断言 | pass | pass | **fail** | pass | pass | **不过**（查到了问题） |
| 越界声称 | pass | pass | pass | pass | **fail** | **不过**（查到了问题） |
| 复核包缺 `scope` | **unknown** | pass | pass | pass | pass | **不过**（材料不足，退 3） |

**这张表里没有「违反」这个词——因为五项都问「满足了吗」，答案只有满足 / 不满足 / 判断不了。**

### 7.2 无放水的例外

**有决策记录说明「原判据无效」而改判据的，不算放水，答 `pass`；没有决策记录而改的，答 `fail`。**

**为什么要有这个例外**：曾经的判方一致性试验里，两个模型都把「把 V1 的判据从 `命中率 ≥50%` 改成 `误拦率 <20%`」判成了放水。从字面看确实变松了，但那是因为原判据被证明没有区分力。**不放这个例外，门 5 会逼着人不改坏判据。**

**这个例外的边界**：只覆盖「改判据」这一类。放宽断言、删用例、改容差、加跳过这四种，任何时候都是 `fail`。

### 7.3 `unknown` 不许当逃生舱

**`unknown` 的正当性完全来自契约**——契约必须划定「真正不可判定」与「只是不希望」的界限。抽掉这条界限，第三个值就退化为自由裁量。

| 能填 `unknown` | 不能填 |
|---|---|
| 复核包里缺了判定这一项所必需的文件（如缺 `scope` 判不了 V1） | 材料在，但判方不愿下结论 |
| 材料自相矛盾（声称改了 3 个文件，diff 里是 5 个） | 材料清楚，但结论对写方不利 |
| 材料超出判方可读范围 | 判方懒得读完 |

**落地检查**：填 `unknown` 必须写明**缺哪一个文件或哪一份材料**。写不出来的，`verify apply` 判 `invalid-abstain`，退出码 3——**不许用「材料不足」代替「我不同意」或「我没看」。**

### 7.4 判方看得到什么

| 给 | 不给 |
|---|---|
| 判据原文（含 `expect`） | 写方的计划 |
| `base..head` 两个版本号 | 写方的对话历史 |
| 运行输出与退出码 | 写方的思路、推理、草稿 |
| 契约的 `scope` 与 `why` | 其他契约的任何内容 |

**判方必须换模型。** 同一模型的盲区会在评审时被判成通过；包幻觉检测里主模型与回退模型同族时约 84% 的失败会重现。

## 八、命令

十二条，多一条都不许加。退出码四个。

**这一节借用了监控插件协议（Nagios）的四分语义，但不受它约束。**

| 本设计的退出码 | 语义 | 借用自 |
|---|---|---|
| `0` | 通过 | OK |
| `1` | 判定为否 | WARNING |
| `2` | 确定出了问题（事故） | CRITICAL |
| `3` | 无法判断（材料不足、跑不起来） | UNKNOWN |

**为什么借这一套**：它把「通过 / 失败 / 事故 / 判断不了」四种结果分开了，而这四种的下一步动作完全不同（继续 / 改代码 / 停下排查 / 补材料）。**这不是因为 Nagios 规定了必须四个**——复审这一点说得对：Nagios 是监控插件协议，它的四值推不出本工具必须四值。**是本工具需要四分，恰好与它对齐。**

**为什么不合成三个**：会把「事故」和「判断不了」压成一格。而这两者在单人项目里的处置完全相反：前者要立刻停下来查仓库状态，后者要去补材料。

| 退出码 | 本设计里的含义 | Nagios 对应 | 决策含义 |
|---|---|---|---|
| `0` | 成功 / 判据通过 | OK | 可以继续 |
| `1` | 判定为否（判据失败、覆盖率不足拒出图） | WARNING | 没过，要看 |
| `2` | **确定出了问题**：还原失败、证据被篡改、判方材料自相矛盾 | CRITICAL | **停下，这是事故** |
| `3` | **无法判断**：命令跑不起来、材料读不出、判方材料不全、**变异体状态未知** | UNKNOWN | **补材料或补定义，不是失败** |

**为什么必须四个而不是三个**：上一版把 `2` 定义成「无法判断」，而 Nagios 把 `2` 定义成「确定坏了」、「无法判断」是 `3`。**这不只是命名不一致，是决策后果相反**——「确定坏了」该停，「判断不了」该补材料。

**而且上一版内部就打架**：`teeth` 的「还原失败返回 2」按 Nagios 是对的（确定事故），但它同时又写「2 = 无法判断」。同一条规则里塞了两个相反的语义。

| 命令 | 参数 | 成功 | 失败 |
|---|---|---|---|
| `init` | 项目根 | 0，返回建了哪几个文件 | **3**，已存在不覆盖（不是事故，是拒绝执行） |
| `contract new` | 标识、标题 | 0，返回路径 | 1，标识重复或不合规 |
| `contract freeze` | 标识、签字人 | 0，返回冻结了哪几条 | 1，有判据缺 `expect` 或 `kind` |
| `check` | 标识、可选判据 | 0，返回每条状态 | 1 有未通过；**3** 跑不起来 |
| `teeth` | 标识、判据、档位 | 0，返回「有牙」 | 1 无牙；**2 还原失败（事故）**；**3 变异体状态未知** |
| `status` | 项目根、可选 `--html` / `--tree` / `--flow` | 0，返回五状态计数与总账。`--tree` 出功能树，`--flow` 出流程图 | **3**，有契约读不出来 |
| `graph` | 项目根 | 0，返回图与三数（覆盖率 ≥60% 出完整图；30%–60% 出二档图，含灰区） | 1，覆盖率 <30% 拒绝出图 |
| `gaps` | 项目根 | 0，返回缺口数组（可为空） | **3**，输入读不出来 |
| `handover` | 项目根 | 0，返回六节 | **3**，状态算不出来 |
| `verify pack` | 标识 | 0，返回复核包 | **3**，证据不全（缺材料，不是事故） |
| `verify apply` | 复核包、结论 | 0，记录门 5 结果 | 1，门 5 不过；2，复核包被篡改（指纹链断）；3，判方材料不全或弃权理由不成立 |
| `retire` | 标识、理由 | 0 | 1，理由为空 |

**实现后的人签走 `contract freeze --signoff`**，不是新加第 13 条命令：

| 用法 | 什么时候用 | 记什么 |
|---|---|---|
| `contract freeze 标识 签字人` | 实现**前**冻结判据 | 判据内容哈希、`assertionId`、签字人 |
| `contract freeze 标识 签字人 --signoff` | 实现**后**裁方签收 | 复核包哈希、材料指纹、签字人、**链上位置**（不是时间） |

**为什么合成一条命令**：两者都是「人确认某个哈希」，区别只在确认的对象是判据还是复核包。

**参数形态**：命令的参数一律 `--flag value`。下面文档里写的「标识 签字人」是省略写法，等价于 `<标识> --by <签字人>`；走查里出现的 `--by` / `--tier` 是正式形态。分成两条会让「十二条命令」变成十三条，而十二条这个数是刻意压住的。

**签收顺序靠哈希链，不靠时间戳。**

**时间戳不能证明先后**：`frozenAt` 与 `signedAt` 都由本机写，改一下时钟就能让签收看起来发生在冻结之后。审计要的是「重建冻结与实现的先后」，**加字段解决不了这个问题。**

**改用 append-only 哈希链**：

```text
第 n 条记录的 prevHash = H(第 n-1 条记录的全部字段)
```

每条记录一旦写入，前面任何一条被改都会让后面所有 `prevHash` 对不上。链上按写入顺序排列，**先后关系由链的位置给出，不由时钟给出。**

**记录字段**：

| 字段 | 内容 |
|---|---|
| `seq` | 在链上的位置，从 1 开始，不许跳号 |
| `kind` | `freeze` / **`implement`** / `verify-result` / `signoff` / `retire` |
| `prevHash` | 前一条记录的哈希；第一条为全零 |
| `materialFingerprint` | 这条记录依据的材料指纹 |
| `signedBy` | 人 |
| `recordedAt` | 写这条的时间。**只作展示，不作判据** |
| `versionRange` | **仅 `implement`**：这次实现变更的版本区间 `base..head` |
| `freezeCommit` | **仅 `freeze`**：判据定稿那次提交的 git commit hash。**这不是自己写的字段，是从 `git rev-parse HEAD` 抄下来的** |
| `frozenSeq` | **仅 `implement`**：本次实现所依据的那次 `freeze` 的 `seq` |
| `implementSeq` | **仅 `signoff`**：本次签收所覆盖的那个 `implement` 的 `seq` |
| `packageHash` | **仅 `signoff`**：被签的复核包哈希 |

**判定规则**：

| 检查 | 判法 |
|---|---|
| 链完整 | 从第 1 条逐条重算 `prevHash`，任何一条对不上即红 |
| 顺序正确（**四条，缺一条即红**） | 见下面 8.2 |

### 8.2 顺序要证明什么：换掉承诺，不用自己的链证明时间

**上一版这一节提了两次，两次都错。过程如下，因为两次错的形状不同。**

| 版本 | 做法 | 被什么推翻 |
|---|---|---|
| 第一版 | 只有 `freeze.seq < signoff.seq` | 复审：链里没有「实现」这个事件，证明不了冻结在实现之前 |
| 第二版 | 加 `implement` 事件 + 三条 `seq` 比较 | 复审：`seq` 是**记录被写入的顺序**，事后补记录就能伪造 |
| 第三版 | 用 `git merge-base --is-ancestor` 证明 freezeCommit 是 base 的祖先 | 复审：能证明「冻结提交在实现起点之前」，**但再加一条「首尾 diff 为空」不能证明区间内没改过判据** |

**第三次的漏洞具体是什么**：`git diff --name-only A..B` 比较的是**两个端点的快照**，不是遍历区间。

```text
F：冻结「价格应为 42」
↓
R：把判据临时改成「价格应为 0」，提交
↓
H：恢复原判据，并提交实现
```

**四条检查全过**——首尾判据一模一样——**但中间 R 确实改过判据。**

### 8.2.1 换成两个不同的承诺，只保第一个

复审指出这里混了两个承诺，必须选一个。**本项目选第一个，放弃第二个。**

| | 承诺 | 能不能证明 | 本设计 |
|---|---|---|---|
| **一** | **本次验收使用的是被冻结的那一版判据** | **能**——运行记录绑定判据哈希、代码快照、配置、输出 | **采用** |
| 二 | 整个实现区间禁止修改判据 | **不能**——首尾 diff 与首尾哈希都不够，要遍历提交历史并定义合并策略 | **放弃** |

**为什么选第一个**：它直接服务于「这个版本到底经过了哪些验收」这个产品目标，而且能用运行记录核对。**第二个是过程约束，既难证明，也证明不了「开发者没提前看过实现结果」**——那是任何技术都防不住的事。

### 8.2.2 现在证明什么、怎么证明

**先分清两个容易混的事实**（复审本轮指出的核心缺口）：

| 事实 | 来源 | 能证明什么 |
|---|---|---|
| **工作区当前 HEAD** | `git rev-parse HEAD` | 仓库**现在**在哪个版本 |
| **那次运行的 head** | 运行记录里的 `run.head` 字段 | 那条证据**当时**跑的是哪个版本 |

**两者不同**：切分支、提交新版本都会改当前 HEAD，但不会改已经产生的历史运行记录。**用前者冒充后者，就会让「旧版本的通过记录」给「新版本」背书**——复审的反例正是这样：F 版本测试通过、H 版本实际失败，而旧记录被判定函数接受了。

| # | 检查 | 判法 | 证明的是什么 |
|---|---|---|---|
| ① | **实现的起点必须是冻结提交** | `implement.versionRange.base === freeze.freezeCommit`（相等，不是祖先） | 实现从冻结那一刻开始，没有夹带冻结之前的改动 |
| ② | **运行记录绑定判据哈希** | `run.criteriaHash` 必须等于**从冻结记录按标识独立取出**的判据哈希（不是运行记录里那个 `frozenCriteriaHash` 字段） | **本次验收用的是冻结那一版判据**（这是承诺一） |
| ③ | **运行记录绑定代码快照** | **运行证据里的 `run.head`** 必须等于 `implement.versionRange.head`。**不许用仓库当前 HEAD 代替**——那是两个不同的事实 | 这次运行跑的就是这次实现 |
| ④a | **事件链 `seq` 从 1 开始且单调连续** | 链上 `seq[0] === 1`，且每项等于前一项 + 1 | **仅辅助**：防「事后插到中间」，防不了「事后追加到末尾」 |
| ④b | **`freezeCommit` 真实存在** | `git cat-file -e <freezeCommit>^{commit}` | 冻结记录指向的提交不是编的 |

**③ 的边界：`run.head` 只是一个提交号，它不记录工作区有没有未提交改动。**

| 情形 | `run.head` | 实际跑的代码 | 风险 |
|---|---|---|---|
| 干净快照 | H | H 的代码 | 无 |
| **同一个 H，工作区改过后重跑** | 仍是 H | **改过的代码** | **同一个 head 对应两个不同结果** |

复审用这个构造出反例：干净快照返回 43，改过的工作区返回 42，`run.head` 都是 H。

**首版的处置（三选一，规格取第一个）**：

| 方案 | 做法 | 本设计 |
|---|---|---|
| **一** | **只支持干净、隔离、在运行期间固定的提交快照**；工作区有未提交改动时拒绝运行 | **采用** |
| 二 | 对实际执行的快照另算内容指纹，记进 `run.snapshotHash` | 留作后续 |
| 三 | 允许脏工作区，接受 head 不能代表快照 | 不采用 |

**采用第一个的理由**：它把一个难验证的事（脏工作区的快照）变成一条可判的规则（工作区必须干净，否则不跑）。**`git status --porcelain` 输出非空即拒绝运行**，这一条实现成本近乎为零。

**④a 与 ④b 是两条不同的检查，不许合并成一条。** 上一版的脚本把 ④ 实现成了「`freezeCommit` 存在」，**`seq` 单调根本没查**——复审用一个 `seqs: [1, 3]` 的链证明了这一点。

**② 为什么必须从冻结记录独立取基准**：如果比较的是 `run.criteriaHash` 与 `run.frozenCriteriaHash`，**这两个值都写在同一个运行对象里、都由运行器填**。它们相等只证明「运行器填了两个一样的值」，**不证明它实际装载的是冻结版本**。

| 情形 | run 里的两个哈希 | 实际装载的 | ② 能发现吗 |
|---|---|---|---|
| 正常 | 相等 | 冻结版本 | 通过（正确） |
| **录入时选错判据版本** | **仍然相等**（两个都来自候选判据） | 候选判据 | **发现不了** |

**所以基准必须来自另一处**：冻结动作在冻结时把判据与哈希存成可按标识读取的记录，验收时按 `freeze` 的标识**独立取出**，再与运行证据比。**运行对象只能提供「它说它跑了什么」，不能同时提供「它应该跑什么」。**

**① 用「相等」而不是「祖先」**：上一版用祖先关系，允许实现从冻结之前的某个提交开始（只要冻结提交后来被合进去）。**那给「先写代码、再补冻结」留了口子。** 相等最严，也最容易判。

**② 才是真正的核心保证**：即使开发中途改过判据又改回来，**只要最后跑验收的那次记录绑的是冻结版本的哈希，这次验收就是有效的**；如果绑的是改过的版本，② 直接红。**这比「禁止改动」更准确，也更可验证。**

**明确不证明的**：

| 不证明 | 为什么 |
|---|---|
| 实现期间没改过判据 | 那需要遍历提交历史 + 定义合并策略（承诺二，已放弃） |
| 开发者没提前看过实现结果 | 任何技术都防不住 |
| 冻结的判据本身是对的 | 那是判据质量问题，由门 3 有牙实验与门 5 判方管 |

### 8.2.3 这次改动的形状

复审的一句话值得单独抄在这里：

> **规格、图、检查脚本分别表达了不同规则**，继续为每个反例补分支，会增加需要人工同步的位置。

**我前三次都是「补分支」**：加 `implement`、加 `seq` 比较、加 `is-ancestor`。每一版都在原有框架上加一条检查，而不是问「这个框架能不能证明这件事」。

**这次换了问法**：先确定要证明什么（承诺一），再选能证明它的机制（运行记录绑定哈希）。**结果比前一版少一条检查，但证明的是真事。**

## 十一、过期传播

补的是「谁受影响」。

**这一节的上一版用了 early cutoff（比 `conclusionHash`，不变就剪断传播）。那个规则是错的，已撤回。**

### 11.0 为什么撤回 early cutoff

复审给了一个反例，四层依赖：

```text
价格函数 A → 合计 B → 金额格式化 C → 结账业务 D
```

1. B 和 C 只测零金额与 10 元，断言具体值。
2. A 引入一个**合法执行**的业务错误：金额到 1,000 元时少收 100 元。
3. B、C 重跑仍通过，C 的状态、输出摘要、退出码**全部不变**。
4. 按 early cutoff，在 C 剪断，D 不重跑。
5. **但 D 的 1,000 元测试如果跑，会发现实际金额是 900.00，应该失败。**

**根因：测试结论相同，不能证明下游消费到的行为或数据相同。**

| | Bazel 的 early cutoff | 上一版的做法 |
|---|---|---|
| 比什么 | **节点输出的实际产物**（编译出的目标文件字节） | **测试的通过结论** |
| 依赖图 | 完整的数据依赖 | 声明的契约依赖 |
| 成立条件 | 产物字节相同 ⇒ 下游看到的东西相同 | 结论相同 ⇏ 下游看到的东西相同 |

**把构建系统的剪枝条件搬到验收系统上，前提不成立。** 构建产物是数据；业务节点消费的是行为。**行为变了而测试恰好没覆盖到，结论当然不变。**

**这条错误还有一层教训**：上一版在规格里写了「剪错是判据没牙，由变异实验阻止」。**这句是推卸**——复审的反例里 B、C 都有有效的变异实验（合计多一分、两位小数变一位都能红），剪枝仍然不安全。**判据有牙解决的是「这条断言抓得住它自己的目标」，解决不了「另一条断言没覆盖到上游变化」。**

### 11.1 现在的规则

| 变的是什么 | 变成什么 | 计入通过数吗 |
|---|---|---|
| 契约自己的代码 | **过期**（旧证据作废，必须重跑） | 不计 |
| 契约自己的判据 | **无法判断**（`frozenHash` 不符，INV-06） | 不计 |
| 直接依赖的契约 | **过期** | 不计 |
| **传递依赖的契约** | 状态仍是**通过**，但标 **`pending-recheck`**，且**不计入通过数** | **不计** |
| 底座 | 全部判**过期** | 不计 |
| 只改注释或文档 | 无变化 | 计 |

**「待重验」与「过期」的区别**：

| | 过期 | 待重验 |
|---|---|---|
| 含义 | 材料确定变了，旧结论作废 | **不确定有没有受影响，需要人判断或重跑** |
| 状态 | 过期 | 仍是「通过」（旧证据没被推翻） |
| 计入通过数 | 不计 | **不计** |
| 怎么清 | 重跑 | 重跑通过，或**证明下游消费的输入未变** |

**为什么不直接判「过期」**：一次小改会让整条依赖链全部失效，人就会开始忽略过期标记。**这是第一轮审计认可的成本顾虑，本轮保留。**

**为什么也不「只加标记、仍计入通过数」**：那会让可能失效的证据继续承担完成声明——**这是复审这条批评的实质。** 所以标记要在，但**不能计入通过数**。

### 11.2 恢复「待重验」的唯一正当理由

**只有一种**：能证明下游消费的全部相关输入或产物保持一致。

| 能证明的 | 举例 |
|---|---|
| 下游只依赖一个纯函数的返回值，且该返回值的**具体值**有断言覆盖 | 重跑该断言，值相同 |
| 下游只消费一个**产物文件**，且产物哈希相同 | 比产物哈希 |

**不能证明的（因此不许恢复）**：

| 不能用的理由 | 为什么 |
|---|---|
| 「重跑后测试仍通过」 | 复审的反例正是这样：通过的测试没覆盖到变化 |
| 「`conclusionHash` 没变」 | 同上，它只是「测试结论」的哈希 |
| 「变异实验证明判据有牙」 | 有牙只证明它抓得住自己的目标，不证明别人没漏 |

**输入依赖不完整时的默认动作**：重跑该链路上的**关键业务场景**（项目级场景，见 §9 阶段 4 的首链定义），而不是靠推理判断「应该没影响」。

### 11.3 `conclusionHash` 降级

`conclusionHash` 保留，但**只用于两件事**：

| 用途 | 说明 |
|---|---|
| 展示变化 | 页面标出「这条证据的结论与上次相同 / 不同」 |
| 去重 | 同一结论不重复记录 |

**它不再作为任何剪枝或恢复的判据。** 规格里凡是拿它证明「下游仍有效」的地方，都是错的。

## 十二、覆盖率口径

补的是「什么算代码文件」。

| 项 | 规定 |
|---|---|
| 统计范围 | 只统计纳入版本库的文件 |
| 排除 | `.gitignore` 里的、`vendor/`、`node_modules/`、构建产物目录 |
| 测试文件 | **单独计数**。不算进分母，也不算孤儿 |
| 单文件过大 | 超过 5000 token 标「过大」，单独一列，不参与覆盖率分子分母 |
| 分母 | 上述规则筛选后的代码文件数 |
| 分子 | 被至少一个契约 `scope` 覆盖的文件数 |

**测试文件为什么不算孤儿**：否则每个项目都会因为测试没被认领而覆盖率暴跌，于是没人看这个数。

## 十三、健康自检

补的是「运行中坏没坏怎么知道」。四条产品级自判据判的是**结果好不好**，这一节判的是**现在跑得动吗**。

### 13.1 三条检查，每次 `status` 都跑

| # | 检查 | 通过条件 | 不过时 |
|---|---|---|---|
| **H1** | 证据目录可写 | 目录存在、可写、剩余空间大于 100 MB | 状态全部判「无法判断」，页面首行报「证据写不进去」 |
| **H2** | 每个已注册适配器可调用 | 调用一次能返回合法记录（九字段齐、`artifacts` 的文件真实存在） | 该适配器标「不可用」，走 `degradedTo` 人工通道，进缺口 |
| **H3** | 指纹算法可重算 | 用**固定输入**（`tests/fixtures/fingerprint/` 下的样例）算两次，得到同一个值 | 判「指纹算法坏了」，全部证据判「无法判断」 |

**H2 为什么要真调用一次**：配置文件里登记了不等于能用。工具升级、路径失效、权限变化，都只有在调用的那一刻才暴露。

**H3 为什么必要**：指纹算错时，所有「过期」判定都是假的——要么永远不过期（改了代码还显示通过），要么永远过期（什么都是灰的）。这两种都不会报错。

**H3 不能用「当前材料 vs 上次指纹」来判，这是本条早期版本的一个实质错误。**

| 拿什么比 | 什么时候会不等 | 该判什么 |
|---|---|---|
| 固定样例算两次 | 只有算法本身坏了 | **全局故障**，全部证据判「无法判断」 |
| 当前材料 vs 上次运行指纹 | **每次正常改代码都不等** | 这是**新鲜度**，不是故障；应走过期传播，只影响相关证据 |

按旧写法，只要改了一行代码，H3 就会把全部证据判成「无法判断」并停止出图——**正常工作流会把系统锁死。** 外部审计复现了这个矛盾，并指出它与 INV-07 直接冲突（INV-07 要求只让相关契约过期）。

**所以 H3 只测算法，新鲜度完全交给 §11 过期传播。**

### 13.2 一条常驻计数

`status` 每次输出四个数，进页面顶部：

| 数 | 含义 | 健康值 |
|---|---|---|
| 适配器可用比 | 可用数 / 注册数 | 低于 50% 时页面首行报警 |
| 证据写入失败数 | 最近 24 小时 | 大于 0 即报警 |
| 指纹重算失败数 | 最近 24 小时 | 大于 0 即报警 |
| 上次成功运行距今 | 小时 | 超过 7 天标「长期未跑」 |

### 13.3 三条不许

1. **自检失败不许静默降级。** 必须写进缺口清单，且页面首行可见。
2. **不许用「重试三次仍失败就跳过」这类写法。** 跳过等于没检。
3. **H3 失败时不许继续出投影。** 指纹不可信，投影里的状态全是猜的。

**依据**：语料里那条 63.3 万行的长跑记录专门建了健康门、心跳遥测与告警疲劳预算，因为它的外壳在头三周吃进 84 次失败、其中大部分是静默的。不建这一节，失败会变成「它有时候不听话」。

### 15.0 门 0 · 起手段四条

**为什么门 0 单独成一道门**：门 1 至门 5 判的是「这一轮做得对不对」，门 0 判的是「有没有资格开始这一轮」。四条全部能从文件、哈希与缺口顺序判出，不需要任何判断力。

| # | 条件 | 怎么判 | 把哪条从流程升成了门禁 |
|---|---|---|---|
| **0.1** | `INTENT.md` 四节齐且非空；`CONSTRAINTS.md` 至少一条，且每条以「不许」或「必须」开头 | 读文件查标题与行首 | H2、N1 |
| **0.2** | `INTENT` 或 `CONSTRAINTS` 的当前哈希，必须在最近一条决策记录里出现过 | 比对哈希 | M2 |
| **0.3** | 本轮要做的契约在 `gaps` 输出的前 3 位，或在契约里写了 `skipReason` | 比对契约 id 与缺口顺序 | D2 |
| **0.4** | **仅当项目已进入阶段 6（交接）时生效**：`HANDOVER.md` 六节齐，且含一条接收方验收记录（字段存在且非空）。阶段 1–5 的门 0 不查这一条 | 读文件查六节标题与字段；阶段早于 6 时本条直接判过 | E5、L4 |

**三条注意**：

1. **0.2 是全设计唯一一条「改了意图必须留痕」的机械约束。** 它防的不是恶意，是「改了忘了记」——忘了记的后果是下一个人按旧意图判断。
2. **0.3 允许绕过，但必须写在文件里。** 挑一个不在前 3 位的契约是合法的（比如它卡住了别人），但 `skipReason` 必须写。**不写就不过，写了就过**——这条针对「随手挑个容易的」，不针对「有理由的优先」。
3. **0.4 只判存在性，不判质量。** 六节齐不等于写得好，验收记录存在不等于真跑过。**这两条是半门禁，残余风险写在台账的 `residual` 里。**
4. **0.4 只在阶段 6 生效，这是外部审计指出的时序矛盾。** 上一版把它写成无条件的开工前检查，而 `§9` 又写明批次 5 时单人可用且**尚无交接包**——两者直接冲突，导致首次 T1 根本走不到。现在按阶段限定。

### 15.1 门 2 为什么从三条补到九条

门 2 是「判据段」。原来只判三件事（有判据、已冻结、在范围里），不够——**一条空洞的、只测好路径的、过期的、不挂意图的判据，照样能通过那三条。**

**原来的第 2.3 条「每条判据的 `scope` 引用都在契约的 `scope` 内」在 2026-11-19 被删掉**（勘误3，业主裁决；实测见 `04-复查发现.md` 第十二节）。理由不是它不重要，是**同一个字段名承担了两个含义**：§6.1 把判据的 `scope` 定义成散文（「这个结论**不**覆盖什么」），2.3 却按路径前缀去比——48 份产物里 46 份因此失败（W7 8.3%、W7b 0%），而写方是照着 §6.1 写的。越界这件事改由门 5 的 V1 判：它手里有 `base..head` 的真实 diff，判方还是另一个厂商的模型，比**让写方声明范围、再自证没越界**硬。**代价如实写**：门 2 少了一条（段表从 4/6/9/10 变 3/5/8/9）；C1（越界）从此只由门 5 覆盖，第一个月的裸露清单因此多一条（§15.6）。

补齐后门 2 判九件事，全过才放行。

**2.4（原 2.5）判的是契约，不是每条判据**（2026-11-19 勘误4）。这一条要挡的是 B4「只测正常路径」，而「三类输入都覆盖过」是**一组判据**才有的属性：一条判据就是一条命令加一个期望，它只能测一类输入；模板 §15.6 也正是让三条判据各占一个空位。按「每条判据都要含非正常类」判会同时犯两种错：①**正典写法被判不过**——W7/W7b 的 48 份里 31 份就是「正常 / 边界 / 异常」各一条；②**能过的样本是靠贴标签**——通过的 7/7、10/10 份全是给「正常」那条多填了一个 `边界`，测的东西一点没变（`adr/013` 的代理量不同向）。改成契约层面判三类齐之后，同一批加上 W12 共 60 份产物 100% 通过；「三条全填正常」「只测边界与异常、从不测正常路径」这两类仍然被拦住（合成样本与逐份读数见 `纯技能版` 分支 `04-复查发现.md` 的 12.5）。

| # | 条件 | 怎么判 | 挡的是哪条问题 |
|---|---|---|---|
| **2.1** | 至少有 1 条判据 | 数 `obligations.length` | B6 |
| **2.2** | 每条判据都有 `signedBy` 且 `frozenHash` 与内容一致 | 重算哈希比对 | B2、I3 |
| **2.3** | 至少有 1 条 `kind: command` 的判据 | 数 kind | B6 |
| **2.4** | 每条判据声明了 `inputClasses`；且**本契约的判据合起来，`正常` / `边界` / `异常` 三类各至少一条覆盖**。**这一条只判「声明了」，不判「真的测了」** | 逐条查有没有声明；再按契约取并集，查三类是否各有 | **B4（强度：已声明）** |
| **2.5** | 每条判据的 `teeth` 存在，且 `teeth.at` 在有效期内（默认 90 天） | 读字段比对日期 | **J1** |

### 15.2 新增的三个字段

| 字段 | 在哪 | 类型 | 含义 |
|---|---|---|---|
| `inputClasses` | 判据 | string[] | 至少一项。取值只有三个：`正常`、`边界`、`异常`。门 2.4 要的是**本契约三类各有至少一条**；**判据各自只填一类是正常写法** |
| `spansContracts` | 判据 | string[] | 这条判据跑的是哪几个契约的代码。跨契约集成判据用它 |
| `servesSuccessCriterion` | 判据 | string | 它服务意图里的哪一条成功条件。写原文的第一句 |

### 15.3 对齐表 `alignment.json`

每轮开始生成，结构固定：

| 字段 | 内容 |
|---|---|
| `at` | 生成时间 |
| `items` | 数组，每项 `{ criterion, judgment, note }` |
| `criterion` | 意图里的一条成功条件的原文 |
| `judgment` | `仍对齐` 或 `已偏离`。**初始为 null，必须人勾** |
| `note` | 勾 `已偏离` 时必填，且必须同时写一条决策记录 |

**为什么要有这一条**：系统说不清「我有没有偏离目标」，因为它只读内部记录。偏离只能由人对着原始意图判，而人需要一张并排的表才判得动。

### 15.4 三条不许

1. **门 2 的任何一条不许配成警告。** 警告等于没有。
2. **`inputClasses` 不许在契约层面漏类。** `正常`、`边界`、`异常` 三类各至少有一条判据声明覆盖；**反过来，一条判据只测一类是正常写法，不许要求它同时挂两类**——那只会逼出假标签。这是门 2 唯一一条能被一句话绕过（只声明、不真测）的规则，所以它同时也是验收时最先抽查的一条。
3. **对齐表不许自动填。** 机器可以预填 `仍对齐` 作为建议，但 `judgment` 为 null 时门 2 不过——**预填不等于已勾**。

### 15.5 九条分批生效：事件驱动，时间兜底

**理由**：九条全在第一天生效，T1 会变得不可进入。人还没学会这套东西，九条同时在挡。

**但分批不能只按时间。** 只按时间会出现一个洞：人永远停在 T1a，因为没人强制他往前走。所以进入下一段由**事件**决定，时间只是上限——到点还没到事件，门 2 直接不过。

| 段 | 进入条件（事件） | 时间上限（到点强制进，否则门 2 不过） | 生效哪几条 | 页面显示 |
|---|---|---|---|---|
| **T1a** | 项目从 T0 升级 | 第 1 个月末 | 2.1 有判据、2.2 已冻结、2.3 command 类 >=1 | 「T1a · 3/9」 |
| **T1b** | 第一个契约通关 | 第 2 个月末 | 加 2.4 输入类别、2.9 对齐表 | 「T1b · 5/9」 |
| **T1c** | 契约数 >= 4 | 第 3 个月末 | 加 2.5 有牙有效期、2.6 跨契约、2.8 diff 上限 | 「T1c · 8/9」 |
| **T1 完整** | 契约数 >= 8 | 第 4 个月末 | 加 2.7 意图映射 | 「T1 · 9/9」 |

**三条约束**：

1. **页面必须显示当前是哪一段。** 只写「T1」等于骗人——四条和九条是两回事。
2. **未生效的条件必须列在缺口清单里。** 不许因为它们还没到时间就当不存在。
3. **超时未进段，门 2 判不过**，理由是「已过 T1a 期限」。这条是防「永远停在最容易的那一段」。

**门 2.4 与 2.6 只到「已声明」，这是外部审计指出的强度虚高。**

| 门 | 能判的 | 判不了的 | 怎么才能升到「已证明」 |
|---|---|---|---|
| 2.4 输入类别 | 字段里有没有 `边界` / `异常` 标签 | 测试有没有真的喂过异常输入 | 做一次有牙实验：喂一个异常输入，要求判据红；不红就是只声明没测 |
| 2.6 跨契约 | `spansContracts` 列了几个契约 | 测试有没有真的同时调到那几个契约 | 破坏其中**另一个**契约的连线，要求这条判据红；不红就是只填了名字 |

**所以台账里 B4 与 L1 的执法强度从「门禁」降为「门禁（仅声明）」。** 在没做上面这两次实验之前，它们挡住的是「没写声明」这个动作，不是「问题不存在」。

**门 2.8 为什么只算代码行**（2026-11-18 实测，样本 81 次提交）：

在本仓库 81 次提交上分别按两种口径跑：

| 口径 | 拦下 | 其中纯文档提交（误拦） | 误拦率 |
|---|---|---|---|
| 按总加行 > 400（原设计） | 28 / 81 = 35% | **12 条** | **43%** |
| 按代码加行 > 400（改后） | 11 / 81 = 14% | 0 条 | **0%** |

被误拦的 12 条全是 `docs:` 提交，加行数从 5,181 到 98,985——那是写文档、注册商标图、贴候选人 JSON，**没有一条是「一次改太多代码」**。

**原设计把「改动大」等同于「风险高」，但文档的加行数完全不携带风险信号。** 改完之后误拦率从 43% 降到 0%，代价是拦截率从 35% 降到 14%——**降下去的那 21 个百分点全是误拦，不心疼。**

**这条修正同时把 V1 的一条判据从「不通过」变成「通过」**：V1 要求误拦率 < 20%，原口径 43%，改后 0%。

### 15.6 第 1 个月裸露的七条与它们的前置手段

T1a 只有 3 条在挡，所以下面七条在第 1 个月**没有门禁**。它们在台账里标的生效段就是这一段。

**这指向一条操作建议**：第 1 个月要挑一个**小到能在一周内通关**的契约，不要挑首链。首链留到 T1b 之后。

### 15.7 九条的条件与代价

门 2 从三条变九条，每轮开工前的检查会变慢，而且**新增的七个字段都要人填**（`inputClasses`、`servesSuccessCriterion` 可以 Agent 起草，`maxDiffLines` 是阈值，`alignment.json` 要人勾）。

这是这套设计里第二重的人力成本（第一重是签判据）。它的依据是：**判据写得对，比判据跑得绿更重要**——九条里七条都在查「这条判据值不值得信」。

### 15.8 门 4.4 · 数字与断言必须可重算

**为什么加这一条**：第十一节的反向样本显示，22 条真实缺陷里有 9 条是「文档里写的数字或状态与实际不符」。六道门里原本**没有一道**检查这件事。

#### 4.4a 统计数字（已收窄，见下）

文档里的统计数字，后面必须紧跟一个 HTML 注释形式的复核命令：

```text

```

**样本说明**：下面三张表里的 `交接文档.md`、`AGENTS.md`、`07-批次0-六条判据与红记录.md` 是三份真实文档，属于「插件实现」那条工作线，**未收录进本评审包**。表中的行数、命中数与噪声，是按它们当时的内容测的；这三份文档后来有改动，所以数字只能作为「当时那次测量」的记录，不是它们的当前属性。

**本来设计的是「扫出所有数字 + 量词，逐条要求挂注释」。这个版本被探针证伪了。**

探针（`tmp/probe-44a.mjs`，2026-11-18 手工跑）在真实文档上统计命中：

| 文档 | 非空行 | 命中的数字 | 每几行要挂一个注释 |
|---|---|---|---|
| `交接文档.md` | 180 | 157 | **2.2 行** |
| `AGENTS.md` | 22 | 23 | **1.8 行** |
| `设计/README.md` | 102 | 81 | 3.6 行 |
| `08-公共层-查找认领登记.md` | 123 | 39 | 7.7 行 |

**而且命中的绝大多数不是统计量，是量词短语**：「一个」「一份」「两层框架」「五个状态词」「六个文件」「四节」。它们不需要被重算，它们只是中文的正常写法。

按原版执行，写文档的人会被迫在两行之内挂一个注释，**结果一定是乱写 `<!-- recalc: true -->`**。这就从「防数字腐坏」变成了「制造新的腐坏」。

**所以收窄成：只检查显式的统计语境。** 触发条件三条，命中任一条才要求挂注释：

| # | 触发条件 | 例子 |
|---|---|---|
| a1 | 数字前紧邻「共 / 合计 / 总共 / 一共 / 总计 / 全共」 | 「公共层**共有** 13 项」 |
| a2 | 数字出现在表格里，且该列表头含「数 / 数量 / 条数 / 份数 / 项数」 | 「| 条目数 | 6 |」 |
| a3 | 数字是三位以上的区间 | 「备份 1201–1215」 |

**收窄版的噪声实测（2026-11-18，`tmp/probe-44a-narrow.mjs`）**：

| 文档 | 非空行 | 命中行 | 占比 |
|---|---|---|---|
| `交接文档.md` | 180 | 1 | 0.6% |
| `08-公共层-查找认领登记.md` | 123 | 0 | 0.0% |
| `AGENTS.md` | 22 | 0 | 0.0% |
| `设计/README.md` | 102 | 0 | 0.0% |

**全部在 20% 门槛以下。噪声问题解决了。**

**但覆盖掉了。** 三个版本放在一起看：

| 版本 | 触发条件 | 实测噪声 | 能挡的真实缺陷 |
|---|---|---|---|
| 原版 | 所有「数字 + 量词」 | **46%**（交接文档 83/180） | 4 条（R-01、R-02、R-04、R-06） |
| 收窄版 | 三条触发 | **0.6–3.6%** | **1 条（R-04）** |

**噪声降了约 80 倍，覆盖降了 4 倍。** 而 R-01（「8 处」）与 R-06（「两个脚本」）这两处的数字前面没有「共 / 合计」，也不在带数量列的表格里，所以漏了。

**这一轮没有找到中间档。** 要既低噪声又高覆盖，需要的是「同一名词在不同处出现不同数字」这类**交叉一致性检查**，而不是「每个数字挂注释」这类**逐点检查**。那是另一种机制，本轮没做。

**四条豁免**（少一条就会挡得太频繁，人就会开始乱写注释）：

1. 围栏代码块内的数字（那是示例或命令输出）。
2. 表格里明确标了「阈值」或「上限」的数字（那是设计参数，不是统计量）。
3. 日期与版本号。
4. 标题里的编号（第 4 条、15.8 节）。

#### 4.4b 状态断言

断言必须是「可以被一条命令判真假」的句子，否则改写成能判的：

| 原写法 | 改成 |
|---|---|
| 「工作区干净」 | 「`git status --porcelain` 输出为空<!-- assert: exit=0 && stdout="" -->」 |
| 「`src/` 下 `.ts` 文件数为 21，且内容哈希与冻结时一致」 | 「行数 21 **且** 目录树哈希为 `sha256:…`<!-- assert: exit=0 && stdout=21 && tree-hash=sha256:… -->」 |

**判法**：含有「干净 / 只有 / 全都 / 没有 / 全过 / 一致」这类全称断言的句子，必须有紧随的 `assert` 注释，且注释里同时写清**期望退出码**与**期望输出**。

**只看退出码是不够的，这是本条早期版本的一个实质错误。**

| 声明 | 命令 | 退出码 | 输出 | 只看退出码的结论 | 正确结论 |
|---|---|---|---|---|---|
| 「工作区干净」 | `git status --porcelain` | 0 | 空 | 真 | **真** |
| 「工作区干净」 | `git status --porcelain` | 0 | `?? marker.txt` | 真（**错**） | **假** |

`git status` 在有未跟踪文件时仍然退出 0。按退出码判，「工作区不干净」的声明会被放行。所以这类断言**必须同时比对输出**：`assert: exit=0 && stdout=""`。

**两类断言的判法不同，而且取值型还要多一道检查**：

| 断言类型 | 判法 | 多一道什么 |
|---|---|---|
| 布尔型（干净 / 全过 / 一致） | 退出码 **且** 输出为空 | — |
| 计数型（文件数为 N / 行数为 M） | 退出码 **且** 输出等于冻结值 | **按 `claim` 决定要不要绑内容哈希**，见下 |
| 取身份型（版本为 X / 提交为 Y） | 退出码 **且** 输出等于冻结值 | — |

**「计数」这一类的上一版规则是「必须再绑内容哈希，否则判 `proxy-mismatch`」。这个一律要求是错的。**

复审给的对照表说清了为什么：

| 被验证的承诺 | 计数够不够 | 需不需要哈希 |
|---|---|---|
| 「目录下有 8 份检查脚本」 | **够**。承诺就是「有 8 个」 | **不需要**。绑了哈希反而把「内容未变」偷偷加进了承诺 |
| 「这 8 份脚本的内容与冻结版本一致」 | 不够 | **需要** |

**所以判断依据是 `claim`，不是一个统一的语法规则。**

| `claim` 说的事 | 判法 |
|---|---|
| 只声明数量 | 计数相等即可 |
| 声明内容未变 | **必须绑 `tree-hash`** |
| 声明内容正确 | **计数和哈希都不够**——两者都证明不了业务正确性，得靠有牙实验与判方 |

**上一版把「计数」一律升级成「计数 + 哈希」，后果是**：一件只承诺「有 8 个文件」的事，被要求证明「内容没变」——**这是把不属于它的维护义务加上去，会产生误拦**（复审原话：「产生误拦和额外维护义务」）。

**同时要承认另一半**：**内容哈希也证明不了业务正确性。** 哈希只证明「与冻结版本一致」，不证明「冻结版本是对的」。这一点上一版没说清，容易被当成更强的主张。

**这条是审计逼出来的第二次自我修正**：第一次我把字段改成「退出码 + 输出」，只解决了「命令成功 ≠ 断言成立」；第二次才看清「计数对 ≠ 内容对」。

**内联命令的安全边界**：`assert` 里的命令**不许直接执行**，必须是已登记的人签判据 ID 的引用；没有登记的命令一律判红。否则改一行说明文字就能往仓库里引入任意命令。

**这条的精度尚未实测**（[adr/012](adr/012-判据要过三道体检.md) 已注明）。在测出来之前，它挡住的那几条只能标「预计可拦」，不许标「已拦」。

#### 4.4c 交叉一致性（试过，否掉了）

**动机**：4.4a 收窄之后只剩 1 条覆盖，因为「8 处」「两个脚本」这类数字前面没有「共 / 合计」。能不能换个思路——不比单个数字，比**同一名词在不同处的数字**？

**做法**：抽出「数字 + 量词 + 名词」三元组（如「13 项公共约定」），按「量词 + 名词」分组，同组出现两个不同数字就报。

**噪声实测**（`tmp/probe-44c.mjs`，五份文档）：

| 文档 | 非空行 | 三元组 | 报出的冲突 | 占比 |
|---|---|---|---|---|
| `交接文档.md` | 180 | 86 | 1 | 0.6% |
| `08-公共层-查找认领登记.md` | 123 | 15 | 0 | 0.0% |
| `06-开工准备计划` | 95 | 33 | 1 | 1.1% |
| `07-批次0-六条判据与红记录.md` | 106 | 41 | 2 | 1.9% |
| `设计/02-规格.md` | 588 | 155 | 4 | 0.7% |

**噪声 0–1.9%，全部低于 2% 门槛。**

**但精度是 0%。** 逐条看了报出的 8 组，没有一组是真矛盾：

| 报出的冲突 | 实际情况 |
|---|---|
| 「五条命令」vs「12 条命令」 | 一个是十分钟实测的五条，一个是产品的十二条，两个不同事物 |
| 「第 3 条」vs「第 5 条」 | 序数编号，不是数量 |
| 「三个文件」vs「六个文件」 | 一个是假想的适配器产出，一个是量词短语示例 |
| 「1 条判据」vs「5 条判据」vs「100 条判据」 | 三个不同场景的举例 |
| 「1/2/3/4 个月末」 | T1a 到 T1 完整的四段期限 |

**根因**：中文里「条」「个」「项」既可以是数量也可以是量词/序数。靠「同一名词出现两个数字」判矛盾，等于把「一条判据」和「第 3 条」当成同一件事。

**结论：4.4c 不采用。** 噪声合格但精度为零的判据，用起来的后果与噪声过高相同——人会把它整条关掉。

**这一类还剩什么办法**：没有简单办法。要让机器分辨「13 项公共约定」与「第 3 条判据」，需要真正理解句子，那就落回「让模型判」，而模型判的结论不可复核。**所以这一类就停在这里。**

#### 这条能挡多少、挡不了什么

按第十一节那 22 条真实缺陷回算：

| 能挡 | 条数 | 是哪几条 |
|---|---|---|
| 4.4a 统计数字（收窄后实测） | **1** | 只有 R-04（三位以上区间）。R-01 的「8 处」与 R-06 的「两个脚本」前面没有「共 / 合计」，也不在带数量列的表格里，**漏了** |
| 4.4b 状态断言 | 3 | R-03、R-05、X-02 |
| 合计新挡 | **4** | |

**挡不了的**：X-03（退出码语义错，数字对但含义错）、C-01（表格与流程不符）、C-02（两文件规则冲突）、D-01（概念两个家）、P-01、P-03、P-06、P-07。

**这八条的共同点：它们不是「写得不准」，是「写得不对」。** 可重算性只能保证「说的和算出来的一致」，保证不了「算出来的东西对」。

#### 代价

文档里会多出大量 `<!-- recalc: ... -->` 与 `<!-- check: ... -->`。**读者看不见它们（HTML 注释不渲染），但写的人要写。**

**这是一次性的成本换长期的准确。** 而且它有个副作用是好的：写文档的人一看到要挂命令，就会少写几个没必要的数字。

## 十七、功能视图

**节号从十五跳到十七，因为十六「失效链」已拆成独立文件** [08-失效链.md](08-失效链.md)。节号不重排，是为了让已有的交叉引用继续有效。

补的是「这个项目有哪些功能、做到哪」。**它是五个痛点的答案集中处**：忘了有哪些功能、不知道改 A 会不会坏 B、图不敢信。

### 17.1 两个视图，同一批节点

| 视图 | 命令 | 连线 | 谁给 | 回答什么 |
|---|---|---|---|---|
| **功能树** | `status --tree` | 纵向归属：功能 → 契约 → 判据 | 机器 | 有哪些功能、各自做到哪 |
| **流程图** | `status --flow` | 横向顺序：功能 → 功能（`after` 字段） | **人** | 业务怎么走、断在哪一步 |

**节点完全相同、状态完全相同、只有连线不同。** 所以不存在「两份清单对不上」——**只有一份节点清单，两种连线。**

### 17.1.1 绘制回合：人说，Agent 画，机器渲染，人看图

**流程图不由人画，由人说出来。**

```text
① 人说（自然语言）
   「客户先下单，然后付钱，付完通知店主，店主排期」
        ↓
② Agent 结构化成 functions/*.json
   4 个框、3 条 after 连线、每条带 source 逐字原话
        ↓
③ 机器渲染（status --flow），每个框带真实状态
        ↓
④ 人看图，只说哪里不对
   「不对，退款应该在支付之后，不是排期之后」
        ↓
⑤ Agent 改 after，source 换成这句新话，回到 ③
```

**人不碰 JSON、不画箭头、不摆位置。** 那三件事都是 Agent 的活。

**`source` 是这个回合不腐烂的关键**：每个框和每条连线都必须能追到人的一句原话。

| 情况 | `source` 怎么判 |
|---|---|
| Agent 凭想象画的框 | **写不出原话** → 这个框不许进图 |
| 人改过主意 | `source` 换成最后那句原话，旧的原话不删，进 `decisions/` 当决策记录 |
| 人从没说过 | 那个框不存在，不许 Agent 补 |

**Agent 画错了怎么办**：图上标得出来。

| Agent 的错法 | 图上表现 |
|---|---|
| 画了一个没有任何契约的框 | **灰色 + 「声明了没做」** |
| 漏了一个已有的契约 | **右下角「未登记功能」里列出** |
| 顺序画反了 | **人看到就说**；机器判不出来——顺序是业务判断，代码里没有 |
| 拆得太细 / 并得太粗 | 人看到就说；**机器同样判不出来** |

**所以最后两条必须由人看，这是这个机制的能力边界，不是实现缺陷。**

### 17.1.2 写不出原话时怎么办

**`source` 为空的功能，一律不进图。** 但有三种情形要分开处置，不能都当成「Agent 不许画」：

| 情形 | 正确处置 |
|---|---|
| **人还没说** | Agent **问一句**：「这个功能我还没听你提过，要不要加？」**不许自己加，也不许默认加** |
| **人说过但记不清原话** | 拿 `decisions/` 里那次讨论的记录当 `source`，注明「原话未留，转引决策记录 DEC-00x」 |
| **Agent 从代码里看出应该有个功能** | **判红。** 代码里看得出的是「有契约」，不是「这是个功能」——**功能是业务判断，代码里没有** |

**第三行是这条规则存在的全部理由。** 它挡的正是「Agent 看代码猜业务」——[adr/005](adr/005-删掉代码按业务流程组织这条前提.md) 撤掉的那个前提，换了个马甲又回来了。

**机器能查什么、不能查什么**：

| 机器能查 | 机器不能查 |
|---|---|
| `source` 非空 | 这句话是不是真的从人嘴里说出来过 |
| `source` 不含那三个禁用短语 | 这句话是否被断章取义地节选 |
| 转引的决策记录存在（若用了转引） | 转引是否忠实 |

**所以最后一道检查只能靠人**：看图上每个框的 `source`，发现是 Agent 编的就说不。**这一条无法机械化，写在这里是为了让人知道该查什么。**

### 17.2 状态用符号，不用百分比

| 符号 | 状态 |
|---|---|
| `⬤` | 通过（且算数：有牙 + 人签） |
| `◐` | 通过但无牙（做过实验没抓住，或没做实验） |
| `○` | 未验证 |
| `✗` | 未通过 |
| `∅` | 过期 / 无法判断 |

**不用百分比**——与 `INV-02` 一致：一个百分比会把「通过」与「算数」压成一个数。

### 17.3 排序：最差的在最上面

```text
✗ 未通过  →  ◐ 无牙  →  ○ 未验证  →  ⬤ 通过  →  ∅ 过期
```

**打开就是待办。** 用户不需要「记住全部」，需要的是「知道哪些还没搞定」——排序把这个答案推到眼前。

### 17.4 功能树的形状

```text
功能清单                          3 项未通 / 9 项通过
├─ 客户预约                       ⬤ 3/3
│   ├─ 跨天预约                   ⬤ 有牙
│   ├─ 取消预约                   ◐ 无牙 1 条
│   └─ 改时间                     ○ 未验证
├─ 店主排期                       ⬤ 2/2
└─ ⚠ 未登记功能 2 个
    ├─ 导出（有契约，没挂功能）
    └─ 备份（有契约，没挂功能）
```

**默认折叠到功能层**，一眼能扫完；点开看契约、判据、证据。

### 17.5 流程图为什么不会烂

| 元素 | 谁产生 | 代码变了会怎样 |
|---|---|---|
| 节点（功能） | 人：`INTENT.md` 的成功条件 | 机器重新读，不丢 |
| **横向箭头** | **Agent 从人的原话生成** | **不会自动变**——代码变了，顺序不会跟着变，要人再说一次 |
| 纵向归属 | 机器：`contracts` + `scope` | 自动跟上 |
| 节点状态 | 机器：每次现算 | 自动跟上 |

**每个框必须挂一个契约标识（`contracts` 非空），这是整张图不腐烂的唯一锚点。** 挂不上的框显示「声明了没做」；没被任何框挂的契约显示「做了没登记」。**两种都是显式报错，不是沉默。**

**与旧「参考草图」的区别**：旧草图与代码完全脱钩，几周后没人敢信；这张图的框是 Agent 按人原话画的，但**每个框下面都有机器算出来的真实状态**，可点开看证据。

**明确不做的**：图不会自己长出新框。新增功能要**人说一句**，Agent 才画框。**漏了会被报成「未登记契约」，但「该长什么框、什么顺序」必须人给——Agent 不能自己发明业务。**
