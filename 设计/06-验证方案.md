# 验证方案：这套设计怎么才算被验证

**这份文件干什么**：把「一个人按这套做，长周期项目成功率高」这个命题拆成能测的部分和测不了的部分，给出五条验证的数据来源、做法、指标、判据与成本。

**为什么必须写这一份**：前八轮一直在完善设计，但**核心命题一条证据也没有**。不写这一份，这套设计永远只能是「有道理」，不能是「被验证」。

---

## 一、命题拆三层

| 层 | 命题 | 需要什么才能验 |
|---|---|---|
| **机制层** | 每道门能拦住它声称要拦的东西，且不误伤 | 一个真实项目的提交历史 + 人工判定 |
| **集成层** | 这些门合起来跑，人愿意用、用得动 | 时间记录 + 交接实测 + 判方一致性 |
| **结果层** | 用了之后项目更少烂尾 | 多项目、长周期、对照组 |

**三层不是一回事。** 机制层成立不等于集成层成立（可能太难用），集成层成立不等于结果层成立（可能拦的东西不重要）。

---

## 二、能测与不能测

| 层 | 单人 + 单机能不能测 | 说明 |
|---|---|---|
| 机制层 | **能** | 用历史数据回放，不需要真跑系统 |
| 集成层 | **能** | 用真人计时与模型一致性测 |
| 结果层 | **不能** | 需要 N≥30 个项目、≥6 个月、有对照组。**一个人做不到** |

**这一节的结论直接决定了产品文档该怎么说**：可以说「机制有效」（有验证方案且可以做），**不能说「成功率高」**（做不了这个测量）。

---

## 三、五条验证

### V1 · 追溯回放：六道门在真实提交上会不会拦

| 项 | 内容 |
|---|---|
| **数据** | 一个真实项目的 git 历史，≥100 次提交、跨 ≥3 个月、单人开发 |
| **做法** | 分层抽样 40 次提交；对每次提交逐条判六道门会不会拦；记录「拦了」或「放行」及理由 |
| **指标** | ① **误拦率**（拦了但其实没问题的比例，人判）② 拦截率（描述性，不作判据） |
| **判据** | 误拦率 < 20%。**门槛只有这一条。** |
| **无基线说明** | 误拦率**没有可比基线**——不存在一个「更松的门禁」可以拿来对照。所以这条只能靠人判，接受这个弱点。凡是没有基线的百分比判据，都必须这样写一行 |
| **成本** | 2–3 天人力 |
| **推翻条件** | 误拦率 > 50%，说明门禁设计与真实工作方式不匹配，应整体重做而非微调 |

**这条最强的理由**：它不需要系统存在。只要有 git 历史和一个懂设计的人，就能做。

**「命中率」这条指标已经被试跑证伪，见第九节。** 现在 V1 只剩「误拦率」一条判据，靠人判。

---

### V2 · 有牙实验的可操作性：人做不做得出来

| 项 | 内容 |
|---|---|
| **数据** | 20 条真实判据（来自一个真项目，不是编的） |
| **做法** | 逐条做档 A 有牙实验，记录：能否写出 `breakPatch`、走了 A1/A2/A3 哪一级、耗时、失败原因 |
| **指标** | ① 成功率（能做出一次有效改坏的比例） ② 中位耗时 ③ 各档占比 |
| **判据** | 成功率 ≥ 70%；中位耗时 ≤ 5 分钟/条；A3（Agent 提议）占比 ≤ 30%。**另需基线**：另取 20 条随手写的判据做同样实验，要求真实判据的成功率至少比它高 20 个百分点——否则「70%」只说明这类动作容易做，不说明这些判据写得好 |
| **成本** | 1 天 |
| **推翻条件** | 成功率 < 50%，说明门 3 对单人不可行，整套设计最硬的一道门不成立 |

**为什么 A3 占比要设上限**：A3 是 Agent 提议改坏方式、人确认，有自证成分。如果七成判据都靠 A3，「有牙」就退化成「Agent 说自己有牙」。

---

### V3 · 交接成本：十分钟到底够不够

| 项 | 内容 |
|---|---|
| **数据** | 一个跑了 ≥1 个月、≥6 个契约的项目 |
| **做法** | 找 3 个没参与过的人（或 3 个全新会话），只给 `HANDOVER.md`，计时答**四问**：现在做到哪、下一步做什么、怎么验证、**这份文档不覆盖什么**。<br/>第四问是实测后加的：原三问全是考「文档里有什么」，没有一问考「文档里缺什么」。另有一条候选（「你能指出它哪里对不上吗」）**未纳入冻结题本**，先在实验里记，不进判据 |
| **指标** | 四问全对的人数；中位耗时 |
| **判据** | 3/3 全对且 ≤10 分钟 |
| **成本** | 半天 |
| **推翻条件** | 3 人中 ≤1 人全对，说明交接包这个产物没用，阶段 6 的出口判据要改 |

**注意**：新会话与真人测的不是同一件事——新会话考的是文档自包含，真人考的是文档加人的常识。**两个都要测，分开记。**

---

### V4 · 判方一致性：两个模型判同一批改动会不会一致

| 项 | 内容 |
|---|---|
| **数据** | 10 个真实改动，其中 5 个干净、5 个有问题（放宽断言、删用例、越界声称等） |
| **做法** | 两个不同厂商的模型各按五项 rubric 判一遍；同一人再判一遍作对照 |
| **指标** | ① 两模型一致率 ② 与人工结论的一致率 ③ 问题改动的检出率 |
| **判据** | 两模型一致率 ≥ 80%；与人工一致 ≥ 70%；检出率 ≥ 80% |
| **成本** | 1 天 |
| **推翻条件** | 检出率 < 50%，说明门 5 不可靠，只能当提醒不能当闸 |

**这一条最容易做出好结果也最容易做出坏结果**——因为「有问题」的 5 个改动由我构造，可能构造得太明显。所以必须加一条：**那 5 个改动要从真实返工里挑，不许自己编。**

---

### V5 · 单案交替：有门禁的周期返工率是否更低

| 项 | 内容 |
|---|---|
| **数据** | 同一个项目，交替两轮：4 周有门禁 / 4 周无门禁，共 16 周 |
| **做法** | 每周记录：提交数、提交后 7 天内同一文件被再修改的比例（返工率）、当周任务复杂度分档 |
| **指标** | 有门禁周期与无门禁周期的返工率差；分层后差值是否仍在 |
| **判据** | 有门禁周期返工率低 ≥30%，且分层后差异不消失 |
| **成本** | 16 周真实开发 |
| **推翻条件** | 返工率无差异或更高，说明门禁只增加成本没有收益 |

**这条最贵也最弱**：16 周里任务难度不可控，「有门禁那 4 周恰好更难」是常态。所以必须先分层再比，分层后样本会很小——**大概率得出「无法判断」而不是「支持」或「推翻」。**

**预先声明这一点很重要**：如果最后得出「无法判断」，那不是失败，是如实结果。

---

## 四、判定规则

| 结果 | 结论 |
|---|---|
| V1–V4 全过 | **机制层与集成层被支持**；结果层仍未验证 |
| V1 不过 | 机制层不成立，门禁设计与真实工作方式不匹配，整体重做 |
| V2 不过 | 门 3 对单人不可行，最硬的一道门不成立 |
| V3 不过 | 交接包这个产物没用，阶段 6 出口判据要改 |
| V4 不过 | 门 5 只能当提醒不能当闸 |
| V5 不过 | 结果层无证据（不等于推翻，可能是代理指标选错） |
| V5 得出「无法判断」 | 如实记录，不算失败 |
| 任一不过且无法解释 | 整体记「无法判断」，不许记「部分支持」 |

**不许做的事**：不许把「V1–V4 过了」说成「这套设计有效」。它们证明的是「六道门在历史提交上拦得合理」和「人用得动」，**不是「项目更少烂尾」**。

## 五、测不了的那一层与它的代价

结果层需要：

| 条件 | 单人能做到吗 |
|---|---|
| 30 个以上项目 | 不能。一个人一年做 2–3 个 |
| 每个跑 ≥6 个月 | 不能。时间不够 |
| 有对照组（同人同期做不用的项目） | 不能。人会混淆 |
| 成功定义统一 | 不能。「做完」「还在用」「改得动」三种定义结论不同 |

**所以这一层在单机条件下永久不可测。** 这不是方法问题，是资源问题。

**代价要说清**：这意味着这套设计永远停在「机制有据、结果未知」。任何把他说成「提高成功率」的说法，都是超出证据的。

---

## 六、因此产品文档该怎么写

**「成功率高」这个说法不许写。** 要写就写下面三句，而且**三句必须同时出现**：

| # | 该说什么 | 怎么说才不超出证据 |
|---|---|---|
| 1 | **它拦得住什么** | 逐条列，不要给一个总分。每条问题的处置与依据在 [../22-67问题防御矩阵.jsonl](../参考/22-67问题防御矩阵.jsonl) 里，一行一条（处置、执法方式、生效段、证据形态、有无数字） |
| 2 | **它的依据有多硬** | 说清哪几条能指到具体比例或样本，哪几条只是真人自述或设计推理。**不给比例，逐条指向台账** |
| 3 | **它有没有提高成功率** | 「**没有被测量过**」。然后给出本文件这套验证方案，说清哪几条在单机条件下做不到 |

**为什么前两条也不许写成数字**：台账里的处置会随每次评审改动，写成「39 条有机器门禁」这种句子，下次改动它就变成假话。**指向台账，不复制台账。** 这正是本包删除过程叙事、只留规范与参考的同一个理由。

**只给第一句是夸大，只给第三句是自我否定。**

---

## 七、最快能做的三条

按「成本最低、信息量最大」排：

| 顺序 | 验证 | 为什么排这个位置 | 成本 |
|---|---|---|---|
| **1** | V2 有牙可操作性 | **最硬的门最容易证伪**。如果人做不出有牙实验，后面全不用做 | 1 天 |
| **2** | V1 追溯回放 | 不需要系统存在，只要 git 历史。信息量最大 | 2–3 天 |
| **3** | V4 判方一致性 | 决定门 5 是闸还是提醒 | 1 天 |

**先做 V2 的理由**：门 3 是整套设计里唯一「机器能验、不靠人诚实」的环节（见 ADR-007 的讨论）。它要是不可行，三方分离、判据冻结、状态现算这一串都失去支点。

---

## 八、这份方案自己怎么被验

| 判据 | 标准 |
|---|---|
| 五条验证都能由一个人做完 | 是。V1–V4 总成本 ≤ 1 周，V5 不要求做 |
| 每条都有推翻条件 | 是。五条全有 |
| 每条都有成本估计 | 是 |
| 不许靠「作者自评」通过 | 是。V1 与 V4 都要外部判定或人工对照 |

**反证已内置**：每条的「推翻条件」就是给这个方案自己准备的反面。**如果五条全过却没能推翻任何东西，要怀疑的是判据太松，不是设计太好。**
