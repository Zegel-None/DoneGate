# 走查：一个真实项目从 T0 走到 T1

**这一份是什么**：把一个真实项目的一次完整循环，按小时拆开，写清每一步跑什么命令、看到什么、谁签字、证据落在哪。

**重要声明**：这是一份**设计走查**，不是实测记录。里面的命令与输出是设计规定的形态，不是某次运行的真实日志。**这套东西还没有实现，所以不可能有真实日志。**

**用的项目**：一个单人做的摄影工作室预约排期工具。客户选套餐、选时间、店主确认、自动提醒。这个项目是真实的（语料里有一份 21 天的复盘），规模约 3200 行，其中手写不到 200 行。

---

## 第 0 天下午 · 从 T0 起步（10 分钟）

店主（也就是开发者本人）打开终端。

```text
$ nc init ~/studio
建了 3 个位置：
  INTENT.md          空模板，四节待填
  CONSTRAINTS.md     空模板，上限 12 条
  contracts/         空目录
```

他填 `INTENT.md`：

| 节 | 他写的 |
|---|---|
| 为什么做 | 工作室现在用微信接单，漏过两次预约，客户跑了 |
| 服务谁 | 店主本人，和每周大约 20 位来约拍的客户 |
| 什么算成功 | 客户能自己选时间并收到确认；店主能在手机上看到本周排期；漏单为零 |
| 明确不做什么 | 不做支付；不做样片交付；不做多店 |

「什么算成功」那三条都能被外部观察：「客户能自己选时间」可以点一遍，「店主能看排期」可以打开看，「漏单为零」可以数。

他填 `CONSTRAINTS.md`，只有三条：

```text
不许 改测试文件
必须 每次提交前跑 node checks/smoke.mjs
不许 在客户端存店主的密钥
```

然后写一条冒烟命令，`checks/smoke.mjs`，内容是「起服务、请求首页、看 200」。

**此刻是 T0。** 全套开销：10 分钟，三个文件，一条命令。

---

## 第 1–2 天 · 只用 T0 跑

他按正常方式写代码，每次提交前跑冒烟。**门禁层只跑门 1**，其余五道门不启用。

第 2 天晚上他遇到一件事：改预约时间的格式化函数，把「确认页」的显示改坏了。冒烟没抓住，因为冒烟只看首页。

**这是第一个信号：「改 A 弄坏 B」。**

---

## 第 3 天上午 · 升级到 T1

```text
$ nc contract new booking-create --title 客户提交预约
契约 booking-create 已建，provisional = true

$ nc contract new slot-format --title 时间显示格式
契约 slot-format 已建，provisional = true
```

两个契约，`scope` 各写一段路径：`booking-create` 拥有 `src/booking/`，`slot-format` 拥有 `src/format/`。

他给 `slot-format` 写第一条判据。判据写的是**判什么**，不是**怎么做**：

| 字段 | 值 |
|---|---|
| `id` | `format-shows-local-time` |
| `kind` | `command` |
| `command` | `node checks/format.mjs` |
| `expect` | `{ exitCode: 0 }` |
| `required` | `true` |

然后冻结：

```text
$ nc contract freeze slot-format --by 店主
冻结 1 条：
  format-shows-local-time  frozenHash = 3f9c…a1
```

**注意 `signedBy` 现在是「店主」。** 从此改这条判据要重新签，改一个字符都不行。

## 第 3 天下午 · 第一次有牙实验

```text
$ nc teeth slot-format format-shows-local-time --tier A
读 breakPatch：src/format/time.ts 第 24 行
  from: return d.toLocaleString()
  to:   return d.toISOString()
改坏…… 跑判据…… 退出码 1（红了）✓
还原…… 哈希核对一致 ✓
再跑…… 退出码 0（绿了）✓
有牙（档 A）
```

`teeth` 字段写进契约：`{ at: "2026-11-20T14:32", tier: "A", result: "有牙" }`。

**如果人写不出 breakPatch**（走查里这一步真会发生——店主不熟 AI 写的格式化代码）：

```text
$ nc teeth slot-format format-shows-local-time --tier A
判据没有 breakPatch，尝试降级
  A1 人写：跳过
  A2 回滚最近一次改 src/format/time.ts 的提交…… 找到 a1b2c3「修时区偏移」
     回滚后跑判据…… 退出码 1（红了）✓
     恢复…… 哈希核对一致 ✓
     再跑…… 退出码 0 ✓
有牙（档 A2，回滚式）
```

这条路径的价值：**它把「写不出改坏方式」从死路变成一条降级路径**，而不用手工造补丁。

**如果还原后哈希不一致**，这条命令会返回退出码 2 并报警——因为那意味着仓库现在处于被改坏的状态，是事故。

## 第 3 天下午 · 第一次跑全门禁

```text
$ nc check slot-format
门 1 基线      冒烟通过
门 2 判据      九条全过：1 条已冻结、command 类 1 条、inputClasses 含异常类、
               teeth 在有效期内、挂上了 1 条成功条件、diff 未超 400 行
门 3 有牙      1 条，档 A，有牙
门 4 证据      start / report / end 齐，指纹一致
门 5 复核      待判方
状态：通过（未通关，缺人签）

证据落盘：.node-contract/evidence/slot-format/format-shows-local-time/20261120T1432/
```

`门 5 复核` 是唯一一道机器自己过不了的。他开一个**新会话**，换一个厂商的模型，跑：

```text
$ nc verify pack slot-format
复核包已导出：.node-contract/verify/slot-format-20261120.zip
内含：判据原文 1 条、base..head = a1b2c3..d4e5f6、运行输出
不含：计划、对话、思路
```

新会话里那个模型只看得到这三样，按五项 rubric 判：

| # | 项 | 答 | 说明 |
|---|---|---|---|
| V1 | 范围 | `pass` | 只动了 `src/format/` |
| V2 | 可定位 | `pass` | 判据直接跑的就是那个函数 |
| V3 | 无放水 | `pass` | 没有放宽断言 |
| V4 | 无未覆盖 | **`unknown`** | 时区跨天后会不会错，判据没覆盖——**这一项材料不足** |
| V5 | 无越界 | `pass` | 声称的范围与判据证明的范围一致 |

**V4 答 `unknown`。按 §7.1 的判定规则：没有 `fail`、但有 `unknown` → 门 5 不过，退出码 3（材料不足）。**

**这不是判方无能**——它说明判据没覆盖到那个情形，需要补一条判据，而不是补材料。**判方在这里给出的最有用信息，就是「我知道这里有个洞」。**

于是他补第二条判据：

| 字段 | 值 |
|---|---|
| `id` | `format-crosses-midnight` |
| `command` | `node checks/format.mjs --case midnight` |
| `expect` | `{ exitCode: 0 }` |
| `required` | `true` |

重新冻结（两条一起），重新做有牙实验，重新 `check`，重新 `verify pack`。这次五项全 `pass`：

```text
$ nc verify apply .node-contract/verify/slot-format-20261120b.zip --result pass
门 5 记录：通过

$ nc status
本轮 2 项：通过 2、未通过 0、未验证 0、过期 0、无法判断 0、不稳定 0
其中通过里：算数 1、无牙 0、未做实验 1、待重验 0
契约 slot-format：1/2，通关待签
```

店主签字前先做一件事：**用自己的话讲一遍这个契约在做什么**。讲得出来才签。

```text
$ nc contract freeze slot-format --by 店主 --signoff --attest "时间显示只做格式化，不碰时区推断"
契约 slot-format：通关
```

**「通关」不是第六个状态词**，它是挂在「通过」上的标记：通过 + 有牙 + 人签。缺一条只许标「通过」。

## 第 5 天 · 第二条判据暴露了一个真故障

`booking-create` 的第一条判据跑红了：

```text
$ nc check booking-create
门 4 证据      指纹一致
口径：退出码 1
输出：期望 201，实际 500
状态：未通过
```

他修完代码重跑，绿了。但**同一处第 7 天又红了一次**。这是第二个信号。

**规则**：同一契约连续三轮未通过，停手质疑边界。这已经是第二次，还不够三次，所以继续修。第三次出现时，他应当停下来问「这个契约切错了吗」，而不是继续打补丁。

## 第 12 天 · 第一次出投影

```text
$ nc graph
覆盖率  78%（21/27 个代码文件被至少一个契约认领）
孤儿    6 个文件：
  src/notify/sms.ts
  src/notify/email.ts
  src/config/theme.ts
  src/util/csv.ts
  src/util/id.ts
  src/util/date.ts
空契约  0 个
结论：可以出图
```

**如果覆盖率只有 45%**（真实项目更常见）——这时不是拒绝出图，是降到二档：

| 档 | 出什么 | 人看到什么 |
|---|---|---|
| 一档（≥60%） | 完整图 + 三色线 | 结构 |
| **二档（30–60%）** | 只画已认领部分，未覆盖面积画成**占据画布的灰块** | 「有一大片我不知道谁管」，比一个 45% 更容易动手 |
| 三档（<30%） | 不出图，只出孤儿清单 + 最少增补建议 | 一份待办 |

**灰块必须占据画布**，不能只在角落写一行 45%。这条如果做错，二档图会被当一档读，等于没有降级。

6 个孤儿不是错，但它们必须被看见。店主看一眼，把 `src/notify/` 归到新契约 `notify` 下，把三个 util 留着当底座（底座不用契约认领）。

再看三种线：

| 线 | 数量 | 含义 |
|---|---|---|
| 实线 | 4 条 | 契约间声明的依赖，代码里也真有引用 |
| 虚线 | 1 条 | `booking-create → notify` 声明了，但代码里还没接上 |
| 红线 | 0 条 | 没有代码引用契约没声明的 |
| 不可见 | 2 处 | 动态拼的模块名，静态分析看不见 |

**那条虚线进缺口清单。** 红线是错，虚线是缺口，两者都画，颜色不同。

## 这一次走查里，哪些动作是机器做的，哪些必须是人

| 动作 | 谁 | 能不能自动 | 证据强度 | 依据 |
|---|---|---|---|---|
| 填意图四节 | 人 | 不能 | **无** | 没有任何材料证明「人写意图」优于「Agent 起草人审」。这是设计立场，不是结论 |
| 填约束 | 人（Agent 可起草） | 不能 | **中** | 约束移出压缩范围有受控实验：完整上下文违规 0%、压缩后 30%、钉住后回 0% |
| 写判据的「判什么」 | 人定，Agent 起草 | 不能 | **弱** | 22% 的自动生成判据效用低，支持「必须人签」；但不支持「必须人写」 |
| 冻结判据 | 人 | 不能 | **中** | 冻结防的是「事后改」，不是「防缺陷」——88,052 个 PR 的研究显示规格有/无不改变缺陷率 |
| 改坏的方式（档 A） | 人写 breakPatch | 不能 | **中** | 有牙实验是唯一能区分「抓得住」与「碰巧对上」的动作；StrykerJS 已在做同一件事 |
| 跑判据 | 机器 | 能 | **强** | 退出码可复现（直读时）；经包装层则取到的是包装层的码，不是判据的码 |
| 算指纹、判过期 | 机器 | 能 | **强** | 29,669 个 AI PR 里 63.2% 改了代码没改文档；未同步文档 30–90 天内再修复率高 8.6–11.7% |
| 五项 rubric | 另一个模型 | 能，但要换模型 | **中** | 745 条 HN 评论里 8 人独立说「不该自己验自己」；同族模型判卷时 84% 失败重现 |
| 签字通关 | 人 | 不能 | **弱** | 没有材料证明人签能提高质量。这是「保留人判断」的立场 |
| 决定重切边界 | 人 | 不能 | **中** | 实现与模块接口之间存在反馈回路，先划死在信息不足时固化错误 |
| 出投影与三数 | 机器 | 能 | **中** | 机械统计可复现；但覆盖率的三个数是设计推理，无实测 |
| 写交接包 | 机器生成，人复核 | 能 | **弱** | 十分钟实测只在本次走查里推演过，没有真实数据 |

**十二个动作里七个必须是人**（表里「能不能自动」答「不能」的七行：填意图、填约束、写判据的「判什么」、冻结判据、改坏的方式、签字通关、决定重切边界）。这就是这套设计的真实分工，不多不少。

## 这次走查暴露的三件事

1. **门 5 的 `unknown` 真的会发生**，而且它是有用的信息——它逼出了第二条判据。设计里那条「说不清计为不过但必须写明哪一项」不是刁难，是主要产出。
2. **投影第一次出图时孤儿一定有**，而且孤儿里有真该归契约的（`src/notify/`），也有本来就该是底座的（`util/`）。所以孤儿必须列出来给人看，不能自动归。
3. **十分钟实测会失败，而且失败点很具体**：不是「文档没写」，是「写的位置不对」。这类失败只有真做一次才会发现。

## 一年时间轴：每个月最可能死在哪一条

前面是小时级走查（一天怎么过）与存量迁移（三周怎么进）。这一节是**月级**：12 个月，每个月最可能死在哪一条链上，以及那个月必须做的那一件事。

**为什么要这个**：67 条问题是静态分类，七条链是静态因果。真实的死法是「第 N 个月被某条链带走」，而人在那个月通常只关心眼前那个功能。

### 12 个月

| 月 | 这个月在做什么 | 最可能死在哪 | 链 | 该月必须做的动作 |
|---|---|---|---|---|
| **1** | T0 起步，建第一个契约（**挑小的，不挑首链**——T1b 要「第一个契约通关」才开门），做第一次有牙实验 | 写不出 `breakPatch`，全部标「无牙」 | D | 走 A2 回滚式；把「未能验证」与「无牙」分开 |
| **2** | 第 2–5 个契约 | 一次一契约太慢，开始并行 | B、E | 批次契约；判方按风险三级 |
| **3** | 第 6–10 个契约 | 约束满 12 条；意图到 60 天 | F、G | 约束常驻/临时分开；意图复核留痕 |
| **4** | 契约数过 8 | 判据爆炸；覆盖率跌破 60% | A、C | 判据守恒（先删再加）；分级出图 |
| **5** | 横向扩展 | 覆盖率持续掉；首批判据 90 天到期 | C | 补 `scope`；判据重做有牙 |
| **6** | 横向扩展 | 同上，且批量签开始出现 | C、A | 签字时长中位数进页面 |
| **7** | 架构债开始咬 | 边界划错，返工贵 | — | 边界重切：受影响证据全部机械作废 |
| **8** | 理解债开始咬 | 说不清自己批过的代码 | — | 每周三条「说不清的地方」 |
| **9** | 接近交付 | 各契约都过，合起来跑不起来 | — | 跨契约集成判据必须存在 |
| **10** | 交付准备 | 技术完成不等于可接收 | — | 接收方对着真实场景跑一遍 |
| **11** | 交接 | 十分钟实测不过 | — | 交接包六节 + 实测 |
| **12** | 维护或退役 | 过期判据越积越多 | — | 重测，或整体标「停止维护」 |

**密度**：链最密的是第 2、3、4 三个月，各有 2 条。**没有一个月到 3 条。** 3 条是我给自己设的过载线——到了就说明那个月该减不该加。

### 延迟爆发表

这张表是这一节最有用的东西。它说：**某件事该在第 N 个月做，不做不会立刻疼，会在第 M 个月疼。** M 总大于 N。

| 该做的事 | 该在第几月做 | 不做的后果 | 第几月爆 |
|---|---|---|---|
| 有牙实验（含降级路径） | 1 | 通过数恒为 0，整套被弃用 | 4 |
| 判方按风险分级 | 2 | 门 5 被跳，自证回归 | 5 |
| 批次契约 | 2 | `overlapsWith` 爆炸，判方只判第一份 | 4 |
| 约束常驻化 | 3 | 删掉最早那条数据安全禁令 | 5 |
| 意图复核 | 3 | 判据全部对齐到过时意图，机制加固错误方向 | 8 |
| 判据守恒 | 4 | 60–100 条判据，人开始不看就签 | 6 |
| 分级出图 | 4 | 覆盖率死锁，永久没有结构视图 | 7 |
| 边界重切 | 7 | 返工成本翻倍 | 10 |

**读法**：如果你在第 4 个月发现「通过数一直是 0」，那不是第 4 个月出的问题，是第 1 个月没做有牙实验。**延迟爆发表的作用是把回溯路径写出来**，让人知道现在该回去补哪一步。

### 三个月过载期怎么减

第 2、3、4 三个月各有两条链同时可能触发，这是全设计的密度峰值。**减的办法不是加机制，是分批。**

门 2 的九条条件如果全在第一天生效，T1 会变得不可进入——人还没学会这套东西，九条同时在挡。所以分四批生效，见 [02-规格.md](02-规格.md) 第十五节第 5 小节。

## 另一个场景：存量项目怎么迁进来

上面那个项目是从零开始的。现实里绝大多数项目已经有几千行代码、一堆测试、一份写过的 README。**迁移的难点不是建契约，是不许一次性建。**

### 第一周 · 只跑 T0

```text
$ nc init ~/existing-project
建了 3 个位置（INTENT.md 已存在，保留原文件不覆盖）
```

只做三件事：把现有 README 里散落的「这个项目要解决什么」抄进 `INTENT.md` 四节；从现有脚本里挑一条**本来就存在**的检查当冒烟；每天跑一次。

**这一周不要建任何契约。** 目的是确认一件事：这个项目的基线是绿的吗？如果冒烟本身就红，先修它——**基线不绿的项目上没有可信的「通过」**。

### 第二周 · 挑一个已经有测试的模块

判据不用从零写。挑一个已经有测试的模块，把现有测试**包成一条判据**。**注意用原生运行器直跑，不要经 `npm test` / `pnpm test`**——包管理器会把「判据的退出码」换成「它自己的退出码」，判据变装饰（规格 §4 明禁）：

| 字段 | 值 |
|---|---|
| `command` | `node --test src/billing` |
| `expect` | `{ exitCode: 0 }` |

这一条的价值不是它新发现了什么，是它**第一次被冻结**——从此改这个模块的测试要重新签字。

然后做一次有牙实验。**大概率会失败。** 存量项目的测试通常做过「为了绿而绿」的调整，改坏之后仍然绿。这一次失败是迁移里最有价值的产出：它告诉你哪部分测试是装饰。

### 第三周到第六周 · 一次一个契约

每周只加一个契约，只加 `scope` 已经稳定、测试已经真的能抓故障的模块。判据数控制在 3 条以内。

**不许做的事**：

- 不许一次性给整个仓库划 `scope`。孤儿清单会一次冒出几百个文件，人会直接关掉页面。
- 不许把「重构之后才可能有的测试」写成判据。判据写现在能跑的。
- 不许为了让覆盖率达标而硬凑契约。覆盖率是症状不是指标。

### 什么时候算迁完

不是「全部代码都有契约」，是三条：

1. 至少有一个契约真正通关（通过 + 有牙 + 人签）。
2. 覆盖率过了 60%，且孤儿清单里每一项都被人看过一遍（看不看的出来不重要，看过就行）。
3. 有一次十分钟实测通过。

**这三条达成，项目就在 T1。** 剩下的代码可以慢慢归契约，也可以永远不归——`scope` 不覆盖的代码在投影里显示为孤儿，孤儿不是错。

### 一条最容易犯的错

迁移时人会想「先把契约划好，再补判据」。**顺序反了就白做。**

先有判据，再有契约：判据决定这个契约要守住什么，契约的 `scope` 应该是由「哪些代码共同保证这几条判据」反推出来的，不是先划一块地再想它该守什么。

这条顺序在新建项目里不明显（因为两者同时发生），在存量项目里是迁移成败的分水岭。
