# ADR-017 · 流程图归人说，节点与状态归机器算

**状态**：已采用
**日期**：2026-11-18

> **后续（不改变本条决定）**：本条标题写「三条硬要求」，正文实际列了四条（1 / 1b / 2 / 3）；`02-规格.md` 现为约 96 KB、十六节，不是十七节。**「人说、Agent 画、机器算状态」这个决定不变。**

## 背景

[ADR-005](005-删掉代码按业务流程组织这条前提.md) 删掉了「代码按业务流程组织」这条前提，连带放弃了「打开图就知道业务走到哪」这个卖点。投影仍然能画，但画的是契约之间的关系，用户要业务流程得自己维护一份草图。

**结果是客户拿到的东西少了一半**：他能知道「哪些契约通过了」，但不知道「客户预约这条路径通不通」。

## 问题

「业务流程」这件事，代码里没有。

- 归属关系（这个功能属于哪个模块）**代码里有**——`scope` 决定，静态可算
- 先后关系（下单之后是支付）**代码里没有**——是业务决定，任何静态分析都推不出来

原文那个「参考草图」的失败教训正在这里：草图与代码完全脱钩，几周后没人敢信；而想让它自动跟随代码，就要求「代码按业务流程组织」，那条前提已被证伪。

## 决定

**同一批节点，两种连线，各归各管。**

| 元素 | 谁产生 | 会不会自动跟随代码 |
|---|---|---|
| **节点**（功能） | **Agent 从人的原话提取，人确认** | 是（机器从清单读） |
| **横向连线**（先后顺序） | **Agent 从人的原话生成** | **否** |
| **纵向归属**（功能 → 契约） | 机器：`scope` 算 | 是 |
| **节点状态** | 机器：每次现算 | 是 |

**三条硬要求**：

1. **每个节点必须挂一个契约标识。** 挂不上就红——这是整张图不腐烂的唯一锚点。
1b. **每个节点与每条连线必须有 `source`（人的原话，逐字引用）。** 空值即红，不许用「基于分析」「根据规范」「从代码推断」顶替（`INV-18`）。**这一条挡的是「Agent 看代码猜业务」——ADR-005 撤掉的那个前提换马甲。**
2. **状态不存。** 图每次从契约现算，与 `INV-01`「状态只有一个来源」一致。
3. **人只说，不画。** 横向连线由 Agent 从原话生成，纵向归属与状态由机器算——**人唯一要动手的是看图并说「不对」。**

## 理由

**一，把「可算的」和「不可算的」分开，是不腐烂的唯一办法。** 混在一起时，机器算不了连线就会退化成「人全维护」，那又回到草图；或者为了让机器算连线而要求代码按业务流程组织，那又回到 ADR-005 证伪过的前提。

**二，锚点让 Agent 画的部分也能被机器盯住。** 图上的框是 Agent 按人的话说出来的，但每个框挂契约 → 契约有状态 → 框上就有真实状态。**这比旧草图强的地方不在画得好看，在每一个框都可点开看证据。**

**三，失效方式变温和了。** 旧图错了会安静地画出一张自洽的错图；新图错了会表现为「这个框的契约找不到」或「这个契约没挂框」——**两种都是显式报错，不是沉默。**

## 后果

**换来的**：客户要的流程图回来了，而且每个框有真实状态；丢弃的只是「机器猜业务顺序」这个做不到的能力。

**放弃的**：**图不会自己长出新框**。新增一个功能要人说一句，Agent 才画框、挂契约；漏了会被报成「未登记契约」，但**框的形状和顺序必须人说，Agent 不能自己发明业务**。

**一条必须接受的成本**：每个契约多填一个字段（挂到哪个功能）。这是 `孤儿契约` 这个计数能成立的前提。

**与 ADR-005 的关系**：那一条删的是「代码按业务流程组织」这个**前提**；这一条恢复的是「业务流程图」这个**视图**。两者不矛盾——视图不需要前提成立，它需要人声明加机器验证锚点。

## 为什么是「人说」而不是「人画」

**这条 ADR 初稿写的是「横向连线由人画一次」。那句话是错的——它等于要人手工编辑 JSON 或拖动节点。**

正确形态是一个五步回合：

```text
人说（自然语言）→ Agent 结构化成 functions/*.json → 机器渲染带状态 → 人看图只说哪里不对 → Agent 改
```

**人只做两件事：说清楚、看图确认。** 不碰 JSON、不画箭头、不摆位置。

**为什么这个区别重要**：

| | 人画（初稿） | 人说（本补正） |
|---|---|---|
| 人的负担 | 编辑结构化数据 | **顺口说话** |
| 谁会画错 | 人（格式、遗漏） | Agent（理解、拆分） |
| 错了怎么发现 | 靠自己复查 JSON | **看图，图上带状态** |

**Agent 画错了图上也看得出来**：画了没契约的框 → 灰色「声明了没做」；漏了已有契约 → 「未登记功能」里列出。**但顺序画反、拆得过细，机器判不出来——那是业务判断，只能人看。**

**新增一个字段 `source`（必填）**：每个框和每条连线都必须逐字引用人的一句原话。**Agent 写不出原话的框，不许进图。** 这是防止 Agent 自己发明业务的唯一锚点。

## 为什么这一节留在 `02-规格.md` 而不单独拆出

[adr/016](016-按引用冲突条件拆出失效链.md) 把「失效链」拆出去，理由是**读者冲突**：失效链只给评审与排期看，其余节给实现者看。

**功能视图不满足这条**：

| 判据 | 功能视图 |
|---|---|
| 有唯一读者吗 | 没有——**实现者要读**（怎么填 `contracts`、怎么算两个计数），**呈现层要读**（怎么渲染树与图） |
| 与其余节耦合吗 | 强耦合——功能对象在 §2.3.1，两个计数在 §3.3.1，命令在 §八 |
| 拆开后跨文件引用会变多吗 | 会——至少三处（§2.3.1、§3.3.1、§八）要指向新文件 |

**所以不拆。** `02-规格.md` 现在约 89 KB、十七节，仍然是全档案最重的一份。**下次要拆，条件仍是「某一节出现了唯一的、与其余节不同的读者」，不是「又大了」。**
