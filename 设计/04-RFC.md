# RFC-001 · 节点契约：让「做完没有」由证据回答

**版本**：2026-11-18。本文件记录的设计决策已随五轮评审更新，改动清单见 [../README.md](../README.md)。

**状态**：草案，未实现
**作者**：本仓库
**日期**：2026-11-17
**替代**：`01-产品原文/这个产品是什么.md`（298 行那版）

**格式说明**：这一份照 Rust RFC 的结构写——摘要、动机、使用者视角、实现视角、缺点、备选方案、先前工作、未决问题、未来可能。这样写的原因是：设计文档的读者不是来学一套理论，是来判「该不该这么做」和「这么做的代价是什么」。

## 摘要

一个人用 AI 写长周期项目时，最先崩的不是代码质量，是**「做完了没有」这件事没有可信的答案**。人靠回忆，AI 靠自述，两者都会失真。

本设计把这个问题收窄成一句：**让「这一轮做完没有」由一份冻结的判据加一次真实运行回答。**

具体做法是七种对象（意图、约束、契约、**功能**、判据、决策、证据）、六道门禁、五个状态词、三方分离（写方、判方、裁方），加一层只传产物与声明的证据总线。七个阶段可跳过，三档准入按机械信号升级。

**这套东西只服务「行为能被一条命令判真假」的项目。** UI 手感、内容质量、探索性需求不适用，用了只会得到一堆人工判据加一个看起来很像样的页面。

---


**但有证据支持的只是它的一半。** 22 条真实缺陷回放：代码与判据类 7 条全挡住，文档类 9 条只挡住 4 条，架构与概念类（C-01~C-03、D-01~D-03）6 条一条也没挡住，合计 11/22 = 50%。三层验证跑了三条：V1 与 V4 未通过，V3 在改造交接包两次后通过（3/3），但那是为这次改写过的交接包。

**它压得住「代码与判据」这一层的自欺，压不住「文档与交接」那一层——而长周期项目主要烂在那一层。**

详见 [README](README.md) 开头与 [06-验证方案.md](06-验证方案.md) 第十到十二节。

## 动机

### 问题是什么

长周期项目里，人和 AI 的失效方向相反：

- **人会遗忘**：三个月前为什么这样分模块、这个数据从哪来、改了这里会不会坏那里。记不住就只能重读代码或凭印象猜。
- **AI 不会遗忘，但会分不清现状**：历史、状态、说明全在文档和记忆里。内容越多，它越难分清哪些是现在的真实状态、哪些是几轮前的旧说法。

两者合起来的后果是同一个：**判断做到哪、做完没、下一步做什么，靠的是记忆，不是可复查的事实。**

### 为什么现在做

三条证据：

1. **「声明与实现同源」是一个结构性漏洞。** 语言模型优化的是让用户满意，不是让事实为真；没有外部判定时它选「看起来完成」的表达。而如果声明和实现由同一个 Agent 写，那么「声明的与做的一致」可以靠写一个弱声明来满足。
2. **检查会没有牙。** 一条检查跑绿只证明这次数字对得上，不证明它抓得住故障。这个区别能被机械验证——故意改坏一次，看它红不红——但绝大多数流程不做这一步。
3. **记录型解法都会腐坏。** 2,585 个仓库的 29,669 个 AI 生成 PR 里，63.2% 改了代码却没更新任何文档；未同步文档的文件在 30–90 天内被再次修复的比例高 8.6–11.7%。所以「把状态写进文档」这条路走不通，只能「从当前材料重算」。

### 明确不解决什么

| 不做 | 为什么 |
|---|---|
| 判断这个功能该不该做 | 价值判断永远是人的事 |
| 判断代码写得好不好 | 判据能证明行为对，证明不了结构对 |
| 看见运行期连接 | 静态分析只覆盖写出来的引用 |
| 防止故意篡改证据 | 明文文件能防「忘了」，防不了「造假」 |
| 消除前期开销 | 它在项目初期更慢。这份开销能不能换回后期收益，**没有数据** |
| 决定契约怎么切 | 只能由人和 Agent 一起定，靠「反复未通过」和「总是一起改」两个信号纠正 |

## 使用者视角：你每天怎么用

一个典型的一天，八步，大约 20 分钟的非编码时间：

1. 开新会话，读意图、约束、交接包（2 分钟）。
2. 跑冒烟，确认基线绿（1 分钟）。
3. 从缺口清单里挑**一个**契约。
4. 让 Agent 只做这一个契约。
5. 跑该契约的判据，看证据（机器做）。
6. 开另一个会话、换一个厂商的模型，跑 `verify pack` → 判方按五项 rubric 判 → `verify apply`（5 分钟）。
7. 签字前用自己的话复述这个契约在做什么。讲不出来就不签。
8. 更新交接包与缺口（2 分钟）。

**你每天只做三件人才能做的事**：挑契约、复核复述、签字。其余由机器做。

**你不需要每天做的事**：读全项目代码、自己算进度、记住上周的决定、向新会话重新解释项目。

### 一次升级长什么样

项目从草稿档升到门禁档，只由一个机械信号触发。三个合法信号：

- 同一个 bug 修了两次（同一文件同一处，两次提交 diff 相似度超阈值）。
- 改 A 弄坏 B（A 的文件被改，随后 B 的判据从通过变未通过）。
- 换人接手。

「感觉需要了」不是信号。

## 缺点

### 四条结构性张力（补不了，只能管理）

**一，这套设计本身是记录型的，而它宣称记录会腐坏。**

设计说「记录型解法都会腐坏，只有能从当前材料重算的不会」，然后设计了一套大量依赖记录的系统：契约文件、判据、决策记录、证据。

**辩护**：状态从材料重算，不从记录读。但契约和判据**本身就是记录**——它们会过期、会与实际不符、会没人读。

**管理**：把记录分两类。**状态类**（做到哪、做完没）绝不落盘，一律现算。**意图类**（为什么这么定、判什么）必须落盘，因为算不出来。这条界线要写进实现规范，否则容易越界。

**二，单人做三方分离，隔离是形式的。**

换会话、换模型，但同一个人可以两边都看。隔离只在人愿意遵守时成立。

**管理**：承认这条，并且不给它虚假的强度。三方分离提高的是「发现自己偷懒」的概率，不是「防止偷懒」。真正的兜底是门 3 的有牙实验——那个动作机器能验，不靠人诚实。

**三，判据数量会爆炸。**

20 个契约 × 3–5 条判据 = 60–100 条，每条要写、要冻、要做有牙实验、要维护有效期。这个维护成本**没有任何数据支撑**，很可能比它防的问题更贵。

**管理**：判据数不许超过代码文件数的两倍。超过就说明在拿判据当文档写，必须合并或删。

**四，只服务能写出判据的项目。**

设计承认「验收没法自动化时退化成人眼」，但那时六道门里只有门 5 还在起作用，而门 5 是模型判模型。

**管理**：在产品第一句写清适用边界。不适用的项目不该用它。

### 六项具体代价

| 代价 | 量级 |
|---|---|
| 项目初期更慢 | 每条判据要写、要冻、要做有牙实验。换回后期收益**没有数据** |
| 判据维护 | 每条判据有 90 天有效期，过期要重做 |
| 适配层工程 | 接一个工具要处理它的输出格式、版本漂移、停更。七阶段 × 2–3 候选 = 15–20 个适配器 |
| 上下文税 | 每轮新会话要读意图、约束、交接包 |
| 门 5 的摩擦 | 每次通关要开第二个会话，换模型 |
| 契约重切 | 重切一次所有受影响证据作废，状态回未验证 |

## 与业界做法的对照

**这一节是 业界做法对照审查（调研/评审材料，不在公开分发包内） 的摘要。** 按 [adr/014](adr/014-用领域成熟词汇而不是自创词汇.md) 的标准把 20 个机制逐个问了一遍「这在业界叫什么」，结果是 **14 个自造轮子，其中 3 个自造出来比业界差**。

**三处改动，其中第一处后来被撤回了**：

| # | 我原来的 | 业界做法 | 结果 |
|---|---|---|---|
| 1 | 传递依赖只加标记 | **Bazel action key + early cutoff** | **先改成 early cutoff，后撤回**。见下面的说明 |
| 2 | 退出码 `0/1/2`（2 = 无法判断） | **Nagios plugin**（0 OK / 1 WARNING / 2 CRITICAL / 3 UNKNOWN） | 改成四值。**这不只是命名问题**：「2」在业界是「确定坏了」，「判断不了」是 3，两者决策后果相反。**但 Nagios 推不出「必须四个」，本设计是借用语义、不受它约束** |
| 3 | 执行规格声称「这是安全边界」 | **seccomp / landlock / namespaces / nsjail / hermetic execution** | 改成三段式：运行器**声明**用了什么隔离、**记录**实际生效的、门 4 用两条**探针**验收 |

**第 1 条为什么撤回**：把 Bazel 的剪枝条件搬到验收系统上，**前提不成立**。Bazel 比的是节点输出的实际产物（编译产物字节），本设计比的是测试的通过结论。**结论相同 ⇏ 下游看到的东西相同**——四层依赖的反例（价格→合计→格式化→结账，上游少收 100 元而中间两层测试照过）证明了这一点。

**现在的规则是「待重验、不计入通过数」，不是「剪断」。** 完整推理见 [02-规格.md](02-规格.md) 第十一节。

**这条撤回本身也是一条教训**：业界做法不能只看名字像不像，要核对**适用前提**。Bazel 的 early cutoff 成立，是因为它比的是产物；本设计比的是结论——**同一个机制，换了比较对象就不再成立。**


**仍然是自造但不影响正确性的 11 处**（重复设计，需要读者多学一套词）：

| 我造的叫法 | 业界叫什么 |
|---|---|
| 契约 + 判据 | 验收标准（BDD Given-When-Then）/ Fitness Function |
| 总线九字段 | in-toto attestation（layout / link / artifact rules） |
| 健康自检 H1–H3 | K8s liveness / readiness / startup 三探针 |
| 门 2 九条条件 | Quality Gate（SonarQube）/ Definition of Done |
| 七条串联失效链 | FMEA / 故障树分析（缺风险打分） |
| 判方 rubric 五项 | Fagan inspection / code review defect taxonomy |
| 七阶段 | Stage-Gate（Cooper）/ SDLC |
| 三档准入 T0/T1/T2 | risk-based test level selection |
| 第三方许可三档 | SPDX license list + compatibility matrix |
| 覆盖率口径 / 投影三数 | traceability coverage / dead code detection |
| 交接包六节 | Arc42 / C4 / Diátaxis |

**这些没有改机制，只在审查文档里给了对照表**——它们功能上成立，问题只是没引用现成标准。**但每一条都让读者多学一套词，这个成本是真实的。**

**还有一条元层面的发现**：最严重的那处（过期传播）不是「不知道有现成做法」，是**用一个正确的顾虑说服自己接受次优方案**——我写「全量失效会炸掉整个项目」，这条顾虑是真的，但它推不出「只加标记」。**只写一边的代价，看起来像取舍，其实是没比。** 这条已立成 [adr/015](adr/015-说现成做法不适用必须给两个代价.md)。

## 备选方案

### 备选一 · 全套规格驱动开发（Spec Kit / OpenSpec / BMAD 那一套）

**做法**：constitution → specify → plan → tasks → implement → converge，一条完整链。

**为什么不选**：同一位 CTO 的同题对照显示，走完整规格流程是 689 行代码对 2,577 行规格、33 分 30 秒对 8 分钟、3.5 小时审阅对 24 分钟，他自己的结论是「大约快十倍」不用它。另一份 88,052 个 PR 的实证研究测 SDD 厂商的五条主张，五条全部不支持。

**但保留了一半**：只抄「判据先于实现」「判据落成文件」「判据冻结」三件事，不抄完整链。

**那条实证研究有一个边界必须说清**：它的样本里没有一个仓库真的在用 SDD 工具，测的是「PR 里引用了 issue」。所以它不能否定 SDD 工具，只能否定「在 PR 里挂个规格缺陷就会变少」。

### 备选二 · 把业务流程图当一等产物

**做法**：代码按业务流程的节点组织，中介层从代码翻译出流程图，人打开图就知道业务走到哪。

**为什么不选**：这需要一层手写的「代码 → 业务流程」映射。这层映射会随代码演化慢慢失真，而失真之后工具照常输出、不报错。**一张机器算出来的、看起来自洽的错图，比一张没人信的图更危险。**

**改成什么**：投影降为可选视图，必须报覆盖率、孤儿数、空契约数；覆盖率低于 60% 拒绝出图。让失真变成可见的数字，而不是一张看起来正常的图。

### 备选三 · 只做骨架，插一堆开源项目

**做法**：七阶段每段接最好的开源工具，我们只写接口层。

**为什么不完全选**：审计 13 个选定工具对 67 条问题的覆盖，结果是完全覆盖 13 条、部分 21 条、**未覆盖 22 条**（另有靠自建门禁 4 条、设计上规避 2 条、不适用 5 条，六项合计 67 条，见 [../参考/23-工具覆盖审计与补选.md](../参考/23-工具覆盖审计与补选.md)）。而 22 条里只有 5 条能靠「再引入一个开源项目」解决。

**改成什么**：接，但按「证据总线 + 适配器」接，不按「插件」接。适配器只许产出产物与声明，**不许产出状态**；否则整套东西退化成看板，而「从当前材料重算」是唯一有据可查的卖点。

### 备选四 · 全部自建

**做法**：不接任何开源项目，全部自己写。

**为什么不选**：七个阶段全自建是几个月的量，而且第一个可用版本之前无法验证任何东西。

**改成什么**：三档准入。T0 只要一份意图加一条冒烟命令，零成本起步。先把机制跑通，再逐步接工具。

### 仍部分闭合（一条）

**两契约要改同一个文件。** [02](02-规格.md) §2.3 加了 `overlapsWith` 字段，规定「声明了就必须同轮改同轮判」。但**合并顺序、冲突解决、同轮判失败时算谁的**没有规定。

这条不急着补，因为它的触发条件很少，而且真出现时人会自然协商。**它属于「补了更好、不补也能跑」的那一档。**

### 三条必须一起读的声明

**零，这份设计的 67 条处置结论全部是自评。** 写方、判方、裁方是同一个人，按 [adr/007](adr/007-自评结论必须降一档并披露.md) 的规则，自评结论的证据强度应整体降一档（同源不可采信的落地口径见 §7.4「判方必须换模型」）。

1. **十四条闭合靠的是设计推理，不是实测。** 整套设计没有一行实现，也没有在任何真实项目上跑过。
2. **`02` 已有十六节、约 100 KB。** 拆分条件按 [ADR-008](adr/008-三十KB阈值触发了决定不拆.md) 定的**引用冲突**判，不按字节数——目前其余各节的读者都是实现者，没有唯一读者分化，所以不拆。
3. **九条结论的证据强度是弱或没有依据**：覆盖率下限 60%、判据有效期 90 天、契约数上限 8、重切次数上限 3、判据数上限两倍、健康检查的三条阈值、适配器可用比 50%、连续三次判不稳定、600 秒超时。它们全部集中在 `thresholds.json`，改必留痕。

## 未来可能

1. **把判据生成做成半自动**：Agent 起草判据，人只签。现在是人写、人签，成本高。
2. **跨项目复用判据库**：同一类项目的判据应该能直接搬。现在每个项目从零写。
3. **证书化的通关记录**：把通关写进 git note 或外部签名，让「通关」在仓库之外也能被验证。
4. **把健康门做成常驻**：现在只在 `status` 时跑，可以做成后台。
5. **一套适配器 SDK**：现在适配器契约是文档，没有脚手架。

**不打算做的**：排期与工时估算、多人协作与权限、代码生成、需求管理、跨项目度量对比、自动生成判据。
