# 卡 · 三组必红夹具

**它回答的问题**：你怎么证明这个适配器真的会红，而不是永远绿？

没红过的夹具与没红过的判据是同一类东西：它们只是装饰。本卡的每一组夹具都要求**第一次跑就必须红**，改对之后才允许绿。

## 入口条件

- 适配器已能在干净树上真跑出合法 `claim.json`（见 [`卡-适配器实现.md`](卡-适配器实现.md)）。
- 有一份真实的上游产物样本可作正样本（可以是 `--raw-report` 喂进去的落盘 JSON）。
- 知道 `tests/adapters/<tool>/verify.mjs` 这个位置——核侧只从这个目录发现夹具。

## 步骤

1. **搭一个临时项目，别拿本仓当试验田。** 每次夹具都在 `mkdtempSync` 里造一个小项目：复制 `adapters.registry.json`、放一份最小源码、`git init` 后提交一次（适配器要求干净树，不提交就一律退 `3`）。
2. **配四组，一组都不许省**：
   | 组 | 怎么造 | 期望 |
   |---|---|---|
   | ① **正样本** | 真实上游产物 / 真跑上游 | 退 `0`，九字段合法，`claims` 非空 |
   | ② **映射反转必红** | 把「检出问题」的产物改成「无问题」（或反过来），或直接断言映射结果与期望不符 | 核侧判定该红即红；适配器本身仍退 `0`（业务违规不退码，只写声明） |
   | ③ **上游缺失退 3** | `--bin __no_such_tool__` | 退 `3`，不许退 `1`、不许崩栈 |
   | ④ **产物截断退 3** | 喂一份半截 JSON（如 `{"issues":[`） | 退 `3`，且报出缺哪个字段 |
   | ⑤ **非法 `--registry-id` 退 2** | `--registry-id bad@stage4` | 退 `2` |
3. **先跑一遍，确认它会红。** 第一版夹具写完直接跑：**必须至少有一组是红的**——如果第一次就全绿，说明断言写太空（多半只断言了「退出码是数字」）。红了之后再去改实现与断言，直到全绿。
4. **断言要落在具体字段上**，不许只断言退出码。例如「`claim.claims[0].checkedBy === 'c01/crit-xxx'`」「`observation.misconfigCount >= 1`」。
5. **收尾接进核侧统一入口**：夹具写完后跑 `node skill/check-declarations.mjs --verify-adapters`，它会把 `tests/adapters/*/verify.mjs` 全量真跑一遍。

## 出口判据

1. `node skill/check-declarations.mjs --verify-adapters` 退 `0`，且输出里**能看到本砖那一套**（不是被跳过）。
2. 五组齐全，且每组都在输出里留下自己的名字（`c.check('…')` 的第一参数）。
3. **有牙证明**：故意把适配器里的一处映射改错（例如把 `Killed` 映射成 `Survived`），重跑 `--verify-adapters` 必须变红；改回来再跑必须变绿。**这一步不许跳**，它是本卡唯一能证明夹具不是装饰的动作。
4. 夹具自身不往仓库里落产物（用临时目录，`finally` 里 `rmSync`）。
5. 夹具不依赖网络（离线可跑）；确实需要网络的砖，必须在夹具里显式跳过并写明原因，而不是让它偶发失败。

## 业界做法参考

| 参考 | 它做到哪一步 | 本卡的差异与两个代价 |
|---|---|---|
| Stryker Mutation Testing（变异测试） | 用变异体检验测试有没有牙：改坏一处，测试必须红 | 本卡把同一思路用在**适配器**上：改坏映射，夹具必须红。代价：每条砖多一次手工改坏-改回；换来：能证明夹具真的会红 |
| 红绿重构（TDD） | 先写会红的测试，再写实现 | 本卡沿用「先红后绿」，但顺序是反的：先有适配器（因为要摸清上游输出形状），再补会红的夹具。代价：多一轮返工；换来：映射表是对着真实输出写的，不是对着想象写的 |
| `skill/17` §七 的三组必红夹具规定 | 规定映射反转 / 上游缺失 / 产物截断三组 | 本卡加了两组（正样本、非法 registry-id），五组一起才闭环 |
