# 卡 · 准入与登记

**它回答的问题**：夹具全绿之后，怎么让这个工具正式「入网」，并且以后能被淘汰？

三处登记缺一处，这个工具就只是本地能跑的脚本，判定核不会认它；登记了但不接受淘汰，它会变成永久负债。

## 入口条件

- 适配器与五组夹具全绿：`node skill/check-declarations.mjs --verify-adapters` 退 `0`。
- 注册表里已经有条目（第 1 步就占了位，见 [`卡-适配器实现.md`](卡-适配器实现.md) 步骤 1）。
- 工作区干净（登记提交前）。

## 步骤

1. **核对注册表条目八个字段**，一个都不许空：
   `id`（`<tool>@stage<N>`）/ `tool` / `stage`（1–7 整数）/ `role`（`hard` 或 `soft`）/ `checkedBy`（`<契约id>/<判据id>`）/ `protocolVersion`（`1.1`）/ `testedToolRange`（例如 `>=2.6.0 <3.0.0`）/ `blindSpots[]`（**至少一条**，写清它测不到什么）。
2. **`checkedBy` 必须真的能挂上**，不是填个样子。跑 `node skill/check-brick-liveness.mjs --root .`：它会去本仓 `contracts/<契约id>/contract.json` 里找那个 `<判据id>`，**找不到即退 1**（孤儿声明，工具等于白接——声明产出了，但没有任何判据认领它）。
   - 本仓**还没有** `contracts/`（还没自举）时退 **3**，属「无法判断」，不是失败；
   - 已经欠着的孤儿声明可以登记进 `skill/wiring-baseline.json` 冻结，但那份清单**只许变少**：接上线不删除，同样退 1。<br>**这一条是踩过的坑**：2026-11-20 之前 18 个工具的 `checkedBy` 全是占位 `c01/*`，因为接砖时本仓还没有契约，而核侧自动路径都跳过契约查找——结果「18 条声明 + 0 条判据」三项门禁全绿，直到手动跑 `--claim` 才暴露。
3. **`ledger.json` 记一条入网账**：`{ brick, registryId, wiredAtBatch, actionsChanged, note }`。
   - `wiredAtBatch` 填本次批次号；
   - `actionsChanged` 填 **`1`**（刚接进来就改变了动作，符合淘汰制的前置要求）；
   - `note` 写**它到底改变了什么**，不要写「已接入」——写「因它发现 X，导致判据 Y 从无法判断变成有读数」。
3. **`batches.jsonl` 追加一行**记录本批次：`{ batch, at, summary }`，`summary` 写清这一批接了哪几个工具、改了什么动作。
4. **跑准入四件**，全绿才许提交：
   ```text
   node skill/check-declarations.mjs --verify-adapters   → 0
   node skill/check-brick-liveness.mjs --root .          → 0（注册表↔台账一致 + 声明挂靠解析成功）
   node runner/run-stage.mjs --registry-id <id> --root . → 0（干净树上真采一次证）
   node skill/check-escapes.mjs --self-check             → 0（提交前全量自检）
   ```
5. **在 `skill/08-试点读数.md` （私有仓）记真实读数**：它这次运行实际读到了什么数字（例如「检出配置缺陷 3 处」「存活变异 0 个」）。没有读数就不算接入过。
6. **接受淘汰考核**：入网后连续 3 批 `actionsChanged === 0`，`check-brick-liveness` 会判退 `1`，届时必须**拔掉这条接线**或说明为什么它不该拔。想留就得让它真的改变动作，不能靠改台账数字糊过去。

## 出口判据

1. 注册表条目八字段齐、`blindSpots[]` 非空、`testedToolRange` 是版本区间而不是单个版本号。
2. **`checkedBy` 能解析到真实判据**：`node skill/check-brick-liveness.mjs --root .` 退 0，且输出里这个工具不在「欠账」列表中（在里面的必须已经接上线并同轮从 `skill/wiring-baseline.json` 删掉）。
3. `ledger.json` 与 `batches.jsonl` 各有一条对应记录，`note` 写的是「改变了什么」而不是「已接入」。
3. `node skill/check-brick-liveness.mjs --root .` 退 `0`，输出里注册表条数与台账条数相等。
4. `node runner/run-stage.mjs --registry-id <id> --root .` 退 `0`，且 `.donegate/adapters/<tool>/claim.json` 的 `artifacts[]` 里含 `kind: "git-anchor"`。
5. `skill/15-工具接入策略.md` （私有仓）对应行的状态已改成「已接入」并标明 `role`。
6. 三条准入命令的原始输出贴在本轮记录里，不许只写「都过了」。

## 业界做法参考

| 参考 | 它做到哪一步 | 本卡的差异与两个代价 |
|---|---|---|
| 依赖清单 + 锁文件（npm lock / Cargo.lock） | 每一个外部依赖都有版本钉死与来源，升级要显式改锁 | 本卡借「钉住」思想：`testedToolRange` 把上游版本区间钉死，超出即退 `3`。代价：上游小版本升级也要重跑夹具；换来：不会在工具悄悄升级后继续报旧结论 |
| 功能开关（feature flag）的「默认关、可回退」 | 新能力上线不影响主链路，出问题一键关 | 本卡的「接线」是可拔的：3 批无动作即强制拔除。代价：接进来就要持续有用；换来：不留只会在报表里出现的装饰砖 |
| `ledger.json` 的 3 批硬淘汰制（本项目既有） | 已用「批次数 + actionsChanged」判工具是否还活着 | 本卡是它的登记工序，不另立新机制 |
