# 卡 · 选型调研

**它回答的问题**：面对一个或一批 GitHub 开源项目，该单接、组团并存（覆盖族）还是精简二选一？没有传统 CLI 的特殊项目（如带 UI 工具、生成器、规则技能仓）怎么调研它的可提取面？

## 入口条件

- 能写出**缺口与定位句**：当前开发流哪一阶段缺什么能力或工件、现在靠什么兜底、接进来后能喂给哪条判据或哪张下游卡片。
- 手上有待评估的 GitHub 仓库或能力方向。

## 步骤

1. **先用 P1–P4 四条原则判断「并存互补」还是「重复淘汰」。**
   - **P1 先问覆盖四维，再谈数量**：对比候选工具的**数据源、作用对象、语言生态、分析精度**。只要四者不同（例如锁文件扫描、容器镜像层扫描、SBOM 交叉扫描、语言调用图可达性扫描；又如快扫规则引擎与深层数据流引擎），它们就不是重复，删掉会丢一半防线——应组成**覆盖族（Coverage Family）**并存，并在下游配一张 `aggregator` 归并去重卡。只有四维几乎重合的「真重复」（如同类协议压测或同类变更日志生成器），才二选一。
   - **P2 跨阶段底座优先复用**：能跨多个阶段复用的基础工具只装一套，不同阶段喂不同输入参数。
   - **P3 真值源打架时不强行合一**：当两款工具真值源相反（例如以历史迁移脚本为准 vs 以声明式期望 schema 为准），可同时保留但必须写死**谁是唯一真值源、谁仅做只读对账校验**。
   - **P4 必须能写出「它不覆盖什么」**：写不出明确盲区的项目不允许进开发流。

2. **每条候选标清证据档位**，只认三档：
   - **【实测】**：本机或沙箱真装真跑过，亲眼拿到它的导出产物、接口返回或终端输出。
   - **【盘上】**：读过仓库原文（README、LICENSE 原文、CLI/API 文档、源码目录结构）。
   - **【声称】**：只看过简介、星标数或二手推荐。**标【声称】的候选不许直接定稿封装。**

3. **四项必查清单（兼容 CLI、带 UI 项目、服务与知识技能仓）**：
   | 核查项 | 查什么与普适口径 |
   |---|---|
   | **许可证原文** | 读仓库 `LICENSE` 文件而非徽章；确认商业/开源分发与命令行/接口调用边界 |
   | **可提取面（不限 CLI）** | 查它靠什么交出确定性结果：① CLI 无头标志（JSON/SARIF/文件落盘）；② 自带 UI 项目的无头构建导出或后台 REST/JSON 接口；③ 纯规则/设计指南仓库的结构化 Markdown/JSON 清单 |
   | **失败与退出语义** | 搞清它正常产出、发现业务问题、环境崩溃时分别返回什么退出码或响应码，以便在适配器层统一归口为 `0 / 2 / 3` |
   | **维护健康度** | 最近提交时间、是否归档停更（已停更数年的老工具优先用活跃替代品或仓库原生目录约定替代） |

4. **否决与落选同样留据。** 被判定为「真重复」或「停更不接」的项目，用一句话写明原因与对比对象，防止后续换一个 Agent 又重复调研同一批落选项目。

## 出口判据

1. 已明确该批工具是「单点底座」「互补覆盖族（附串联顺序与归并规则）」还是「真重复二选一」。
2. 进入封装阶段的每个项目均达到【实测】或【盘上】档，且已找准它的具体提取面（CLI / 无头导出 / API 快照 / 落盘文件 / 规则文件）。
3. 每个项目均已写出至少一条具体的「不覆盖什么」（对应 `blindSpots[]`）。
4. 结论清晰落在：完整接入、去壳局部提取接入（如只抽带 UI 项目的无头导出或数据层）、或明确不接并附可复核理由。
