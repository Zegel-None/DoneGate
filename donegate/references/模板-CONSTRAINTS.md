# 模板 · CONSTRAINTS.md

## 入口条件

- INTENT.md 已在仓库里，且第四节「明确不做什么」至少有一条（§2.1）。约束从这一节长出来。
- 本轮要改的东西已指认得出来：至少一个文件路径、一条命令，或一处数据。
- 手上有最近三次返工或事故的记录。一条都没有就先补记录，补不出来写的就是猜的。
- 有人能签字。Agent 起草不算，必须人在提交里确认（§2.2）。
- 动笔前读完 §四 的三条禁令，约束不许与它们相反。

## 步骤

1. 把 INTENT.md 的「明确不做什么」逐句问：违反它会做出什么具体动作。一个动作出一行，想不出动作的留在原文。
2. 每行写成「不许 / 必须 + 具体动作」，动词后跟得住具体对象——文件、命令、字段、人。删掉「尽量」「注意」「合理」「规范」，它们判不了真假。
3. 一条只装一个动作。出现「并且」「同时」「或者」就拆成两行。
4. 逐行配检查，按顺序试三种落点：能写成 `kind: "command"` 且 `expect.exitCode` 有确定值的优先；能写出一句 `kind: "human"` 判断标准的排第二（§2.4；**human 判据算一条检查**，G-07）；两样都写不出的进「只靠人守」，条目后写一句为什么对应不上（§2.2）。
5. 数行首匹配「不许」「必须」的行数就是条数；要加新条时按 §2.2 的条数上限腾位置。
6. 逐行请人确认并在提交里署名（§2.2）。没签的那一轮，该条约束不生效。
7. 落盘前过一遍「只靠人守」区：每条都要说得出人做什么动作。

### 可直接改用的四行

```text
不许 把密钥、令牌、真实客户数据写进仓库、测试固定装置、日志或截图；要跑这类流程用假值替身。
  → command 判据：扫仓库与证据目录，命中密钥形态即判红

不许 为了让判据转绿去改测试文件、判据文件或本文件；判据本身写错时改判据并重新冻结（§四 三条禁令第 3 条）。
  → command 判据：跑 check 前后比这两类文件的哈希，变了即判红

必须 判据命令直读子进程退出码，不经包管理器包装（§四）。
  → command 判据：抽查判据命令原文，出现包装层即判红

不许 在没人当场确认时执行删表、删库或改写生产数据。
  → 对应不上：确认是否发生过要读对话记录，机器判不了；human 判据也只能事后追认，所以进「只靠人守」
```

## 出口判据

1. 条数：数行首匹配「不许」「必须」的行，看数字；大于 12 记未通过，「都很重要」不是理由。
2. 落点齐全：逐行找条目后有没有 `command` 判据标识、`human` 的一句判断标准，或「只靠人守」加原因；三样都没有的行记未通过。
3. 证据可查：被点名的 `command` 判据，在 `.donegate/evidence/` 下查到最近一次三份齐全的运行（§2.6）；查不到记约束未验证，命令跑不起来记无法判断（§八），都不许记通过。
4. 能红：抽 3 条，按 §六 A 档各改坏一次再跑对应判据；有一次没判红，那条判据的 `teeth` 记 `survived`，对应约束退回重写，整份不算过。
5. 人签在案：`git log` 里这一轮本文件的改动带人的署名确认（§2.2）；只有 Agent 提交的记未验证。
6. 反向抽查：「只靠人守」区任取一条，问守住它的动作；答不出，或这条能写成 `human` 判据（§2.4），记未通过。

## 业界做法参考

| 参考条目 | 它做到哪一步 | 本卡的差异 |
|---|---|---|
| Spec Kit · `constitution`（N1 首选） | 硬约束写成仓库内文件，每条命令先读它再动手；不限条数，也不要求每条配检查 | 本卡限 12 条，每行必须落到一条判据或「只靠人守」 |
| OpenSpec · `specs/` 的 WHEN/THEN 条目 | 约束写成可判定的场景，随变更归档累积 | 本卡不写场景，只写动作，场景留给 §2.4 的判据 |
| Log4brains · ADR 的 Context 与 Consequences | 决策理由不可改写，只能被新记录取代 | 本卡不存理由（理由归 §2.5），只留可执行的那面 |

两个代价同量比——「一份文件里能被执行的条数」：

- 现成做法不设上限：约束会一直涨（Spec Kit 的 constitution **不要求每条配检查**——这是解法册 N1 的原话，别往外推成「0 条有机器检查」这种具体数字）。
- 本卡压到 12 条：12 条都能配检查；**满了要加就必须先删一条**（§2.2 的规则原文），不是「转进决策记录」——决策记录只用于改判据/边界/意图（§2.5）。
