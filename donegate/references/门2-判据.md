# 门 2 · 判据

**它判的不是「有没有判据」，是「这条判据值不值得信」。** 规则只在 [规格](../../设计/02-规格.md) §15.1–15.7、§四、§6.1；本卡只写怎么操作、按什么顺序、什么算过。

## 入口条件

1. 档位不是 T0——门 2 从 T1a 起才生效（§15.5）。
2. `INTENT.md` 的「什么算成功」已逐条写死，能当 2.7 意图映射的输入。
3. `contract.json` 已存在、本契约 `scope` 已声明；判据与 `scope` 同在一个文件。
4. 上一轮结论在手：`过期` 与「待重验」的判据先处理，否则这轮是在旧材料上判。

## 步骤

1. **先定段，再定今天判几条。** 读 §15.5 段表，**先看事件**：事件到了才进段。**T1b 的事件「第一个契约通关」＝通过 + 有牙 + 人签三条件齐（07-结论 §二 的定义），契约「存在」不算事件发生**——现场没有通关证据就停在 T1a，不许自创「视为已过首关」这类解释。事件没到而时间上限已过，门 2 直接判不过（§15.5 约束 3），不是「按那一段算」，把一行贴进本轮记录：T1a 3 条、T1b 5 条、T1c 8 条、T1 完整 9 条——分母不是固定九，**今天只判当前段生效的那几条**。
2. **写判据三件套。** 每条先落 `claim`（承诺什么，必须能被现实缺陷打破）、`observable`（断言写在哪个具体值上）、`scope`（不覆盖什么）。定义与反例只在 §6.1：一个写法是否空心，看它承诺什么，不看语法。
3. **补三个新字段。** `inputClasses`、`spansContracts`、`servesSuccessCriterion` 的取值以 §15.2 为准；`inputClasses` 只用 正常 / 边界 / 异常；**契约里三类要各有至少一条判据**，而单条判据只填一类是对的。§15.7 只允许 `inputClasses` 与 `servesSuccessCriterion` 由 Agent 起草；`spansContracts` 要人填。三者都必须人签。
4. **冻结与签字。** 写 `signedBy` 与 `frozenHash`，改一个字符就重算重签；门 2 只认重算后与字段一致。**冻结前先取裁方对每条 `scope` 的逐条确认，落 `scopeAck: { by, at }`，`by` 不许是写方自己**（G-10：写方单方面声明覆盖范围正是 M-18 那个洞，这是它最便宜的一步）。
5. **逐条过当前段的条件。** 打开 §15.1 的表，只对第 1 步算出的那几条要结论（写法见出口 2）。
6. **把「已声明」与「已证明」分开记。** 2.4 与 2.6 只判「填了没有」；记成已证明就是虚高，升级要走 [门 3](./门3-有牙.md) 的改坏实验（§15.5 末段）。2.5 读的是 `teeth.at`：**`teeth` 至少写成 `{"status": "<§6.1 唯一清单里的一个值>", "at": "YYYY-MM-DD", "variant": "A|B|C"}`**，`at` 是实验当天；只写 `status` 的，2.5 判不过（有效期 90 天，§15.1 2.5）。
7. **对齐表该人勾就让人勾。** **每轮开始就按 §15.3 生成** `alignment.json`（2.9 只是从 T1b 起才要求它已勾，别等到 T1b 才第一次生成）；预填不算勾；**2.9 生效后（T1b 起）上一轮的对齐表里 `judgment` 留空即不过**——T1a 只有本轮刚生成的表、没有「上一轮」，不按这条判。勾 `已偏离` 须带说明并同时写决策记录（§15.4 第 3 条）。
8. **跑一次，拿真实退出码。** 判据一律 `node scripts/…` 直跑，不经包管理器；退出码 0 / 1 / 2 / 3 原样进证据，三条禁令命中即判红（§四）。

## 出口判据

1. **段位与分母在案。** 本轮记录能读到「当前段位 + 生效 x/9」；只写「T1」或不分段一律按九条判，不过（§15.5 约束 1）。
2. **生效条件条条有读数。** 对当前段生效的每一条都有字段名或命令加读到的值；只写「符合」而无读数，不过。
3. **三件套可当场抽出。** 随机抽一条，能报出 `claim`、`observable`、`scope` 三段原文；缺一段这条判据不算通过。
4. **字段抽查过关——只查当前段已生效的条目。** 2.4 生效时：把全部判据的 `inputClasses` 取并集，三类缺任何一类即不过；**单条判据只填 `正常` 不算错**（§15.4 第 2 条）。2.7 生效时：抽一条报不出 `servesSuccessCriterion` 原文首句，也不过。
5. **对齐表与缺口清单齐。** 2.9 生效时（T1b 起）：`alignment.json` 任一 `judgment` 为 null 不过。**任何段位**：未生效条件漏出缺口清单，也不过（§15.5 约束 2）。
6. **退出码干净，且 `expect` 整条成立。** 本轮退出码是 0 / 1 / 2 / 3 之一且子进程直读；出现吞失败写法、经 `pnpm run` 包装、或改过判据文件，直接判红（§四 三条禁令）。**判据「绿」＝退出码等于 `expect.exitCode`，且声明了 `stdoutMatches` 时实测 stdout 也命中（精确整串相等，不是正则，G-11）**（§2.4）；只对退出码不算绿——这条判据判**未通过**并进总账分母，不许只记缺口放行。
7. **本轮只挑一个契约。** 任务让你做两件事时，只做一件，另一件写进缺口清单并注明「任务与 §9.1 第 3 步冲突」——静默把两件都做完，本条判不通过；两个契约的判据也不许混进同一份总账分母。
8. **`scopeAck` 逐条非空。** 冻结前每条判据的 `scopeAck.by` 非空且不是本轮写方自己；缺一条本条不过（G-10）。**这是卡级出口，不是 §15.1 的第十条**——门 2 仍按当前段 3/5/8/9 判。

## 业界做法参考

| 参考 | 做到哪一步 | 本卡的差异 |
|---|---|---|
| Cucumber（H1 首选） | 场景台词与 step definition 同在一份 `.feature`，人评审读的那句就是 CI 跑的那条 | 无场景文件；承诺写在 `contract.json` 的三件套，红绿由 `node scripts/…` 退出码给出 |
| spec-kit（E4 首选） | 写码前强制把验收场景与独立测试判据落进 `spec.md`，含糊处用澄清命令写回同一份文件 | 不生成 spec；只要求每条成功条件挂到判据（2.7），偏离由人勾 `alignment.json` |
| OpenSpec（H1、E4 备选） | 需求与场景以 requirement + scenario 进仓库，可结构校验与归档 | 结构校验交给门 2 条件与证据，不另做对照命令 |

差异明显的两处按 [adr/015](../../设计/adr/015-说现成做法不适用必须给两个代价.md) 用同一个量比：

| 量 | 现成做法 | 本卡 |
|---|---|---|
| 改一条判据断言要同步几个文件 | Cucumber：2 处（台词 + step definition） | 1 处（`contract.json`） |
| 一条成功条件要写几处 | spec-kit：1 处（`spec.md` 验收场景） | 2 处（`INTENT.md` 原文 + 判据字段） |
| 人能否不读机器文件就评审 | Cucumber：能，场景即文本 | 不能，要读 JSON；句式不统一，`unquantified` |
