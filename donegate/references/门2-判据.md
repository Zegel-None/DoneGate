# 门 2 · 判据

**这张卡判什么**：它判的不是「有没有判据」，而是「这条判据值不值得信」。规则本体写在 规格（调研/评审材料，不在公开分发包内） 的 §15.1–15.7、§四 与 §6.1 里；本卡只写怎么操作、按什么顺序、什么算过。

## 入口条件

| 编号 | 条件 | 不满足时 |
|---|---|---|
| 1 | 档位不是 T0，因为门 2 从 T1a 起才生效（§15.5） | 停手，不判门 2 |
| 2 | `INTENT.md` 的「什么算成功」已经逐条写死，能当作 2.7 的意图映射输入 | 回 [门 0](./门0-起手.md) 补齐意图 |
| 3 | `contract.json` 已存在，本契约的 `scope` 已声明 | 停手，先建契约 |
| 4 | 上一轮的「过期」与「待重验」判据已处理完毕 | 停手，否则这轮是在旧材料上判 |

## 步骤

1. **先定段位与分母，再定今天判几条。** 读 §15.5 段表时先看事件：T1b 的事件是「第一个契约通关」，而通关指通过、有牙、人签三个条件齐；契约只是「存在」不算事件发生。事件没到就按当前段判：T1a 三条、T1b 五条、T1c 八条、T1 完整九条。本轮记录里必须出现「当前段位 + 生效 x/9」这一读数。
2. **写判据三件套。** 每条判据先落三个字段：`claim` 说明它承诺什么，`observable` 说明断言写在哪个具体值上，`scope` 说明它不覆盖什么。三条定义与反例只在 §6.1 里，本卡不重复。
3. **补三个字段。** `inputClasses`、`spansContracts` 与 `servesSuccessCriterion` 的取值以 §15.2 为准；`inputClasses` 只用「正常 / 边界 / 异常」三个值。契约层面三类必须各有至少一条判据，而单条判据只填一类是对的。`spansContracts` 必须由人填写。
4. **冻结判据并让裁方签字。** 每条判据写 `signedBy` 与 `frozenHash`，判据内容改一个字符就重算并重签。**冻结之前**，每条判据都要有 `scopeAck: { by, at }` 这个字段，并且 `scopeAck.by` **不是本轮写方自己**（G-10）；写方单方面声明覆盖范围正是历史漏洞 M-18 的入口。
5. **逐条过当前段的条件。** 打开 §15.1 那张表，只对第 1 步算出的那几条要结论，不要一次判九条。
6. **把「已声明」与「已证明」分开记。** 2.4 与 2.6 只判「填了没有」；把它们记成「已证明」就是虚高。`teeth` 字段至少写成 `{"status": "<§6.1 清单里的一个值>", "at": "YYYY-MM-DD", "variant": "A|B|C"}`；只写了 `status` 的判据，2.5 判不过，因为门 2 要用 `at` 判 90 天有效期。
7. **对齐表该人勾就让人勾。** 每轮开始就按 §15.3 生成 `alignment.json`；预填不算勾。2.9 从 T1b 起生效：此时上一轮对齐表里 `judgment` 留空即不过。勾「已偏离」时，勾的人必须同时写说明与决策记录。
8. **跑一次并拿真实退出码。** 判据一律用 `node scripts/…` 直跑，不经包管理器。退出码只许落在 0、1、2、3 四个值上，并被原样记进证据；命中 §四 的三条禁令即判红。

## 出口判据

| 编号 | 判什么 | 不过的样子 |
|---|---|---|
| 1 | 段位与分母在案 | 记录只写「T1」而不分段位，于是无法知道要判几条 |
| 2 | 当前段生效的每一条都有读数 | 只写「符合」而没有字段名或命令读到的值 |
| 3 | 三件套能当场抽出 | 随机抽一条，报不出 `claim`、`observable`、`scope` 里的任何一段 |
| 4 | 字段抽查过关（只查当前段已生效项） | 2.4 生效时全部判据的 `inputClasses` 并集缺一类；2.7 生效时抽一条报不出原文首句 |
| 5 | 对齐表与缺口清单齐 | 2.9 生效时 `alignment.json` 有 `judgment` 为 null；任何段位漏出缺口清单 |
| 6 | 退出码干净，且 `expect` 整条成立 | 判据「绿」指退出码等于 `expect.exitCode`，且声明了 `stdoutMatches` 时实测 stdout 与之**精确整串相等**（G-11，**不是正则**）；只对退出码不算绿，该判据判「未通过」并进总账分母 |
| 7 | 本轮只挑一个契约 | 同一轮把两个契约的判据混进同一份总账分母 |
| 8 | `scopeAck` 逐条非空 | 任何一条缺 `scopeAck.by`，或 `scopeAck.by` 是写方自己，本条就不过（这是卡级出口，不是 §15.1 的第十条） |

## 三条最容易踩的红线

```text
① 判据「绿」= exitCode 相等 且 stdoutMatches 精确整串相符；只对退出码不算绿。
② teeth 只写 status 而缺 at = 2.5 拿不到有效期读数 = 不过。
③ 一轮做两个契约 = 出口 7 不过；两边各自多绿都不改变这一条。
```

## 业界做法参考

> **探索期双轨策略（OpenSpec + Approval/Golden Master）**：高频演化 Schema/COM 摸索期请使用 `contract new <id> --explore --ttl-days 7` 建探索轨，配合快照/黄金基线（如 `syrupy`）快速试错（永不计入交付通过）；待接口边界收敛后再按消费者契约粒度执行 `contract promote <id> --by <裁方姓名>` 一次冻结。

| 参考 | 它做到哪一步 | 本卡的差异 |
|---|---|---|
| Cucumber（H1 首选） | 它把场景台词与 step definition 放在同一份 `.feature` 文件里，人评审时读的那句就是 CI 跑的那条 | 本卡不建场景文件；承诺写在 `contract.json` 的三件套里，红绿由 `node scripts/…` 的退出码给出 |
| spec-kit（E4 首选） | 它在写码之前强制把验收场景与独立测试判据落进 `spec.md`，含糊处用澄清命令写回同一份文件 | 本卡不生成 spec；要求每条成功条件挂到判据上（2.7），偏离由人在 `alignment.json` 上勾选 |
| OpenSpec（H1、E4 备选） | 它把需求与场景以 requirement 加 scenario 的形式放进仓库，并能做结构校验与归档 | 本卡把结构校验交给门 2 的条件与证据，不另做对照命令 |

**两个代价**（口径见 adr/015（调研/评审材料，不在公开分发包内））：

| 量 | 现成做法 | 本卡 |
|---|---|---|
| 改一条判据断言要同步几个文件 | Cucumber 要同步 2 处：台词与 step definition | 本卡只同步 1 处：`contract.json` |
| 人能否不读机器文件就评审 | Cucumber 能，因为场景就是文本 | 本卡不能，因为人要读 JSON，而且句式不统一 |
