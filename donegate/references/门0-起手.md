# 门 0 · 起手

门 0 判的是「这一轮有没有资格开始」，不是「这一轮做得对不对」。四条的规则本体在 [§15.0](../../设计/02-规格.md)，本卡只写怎么跑、按什么顺序跑、什么算过。

## 入口条件

- 项目根可读，`INTENT.md` 与 `CONSTRAINTS.md` 都在项目根（§2.1、§2.2）。
- 本轮还没有动过任何契约文件；门 0 跑在 §9.1 那七个动作之前。
- 当前阶段已知（§九）。阶段决定 0.4 查不查：阶段 1–5 不查，阶段 6 才查。

## 步骤

按 0.1 → 0.2 → 0.3 → 0.4 的顺序跑。前一条记「未通过」就停，不往下跑，后面的结论会被污染。

**0.1 意图与约束在场。**
1. 取 `INTENT.md` 的二级标题，与 §2.1 的四节标题逐字比对；缺一节即记「未通过」。
2. 逐节看内容：某节标题与下一个标题之间，除空行外一个字都没有，该节判为空，记「未通过」。
3. 取 `CONSTRAINTS.md` 的条目行（§2.2 的格式是「不许 / 必须 + 具体动作」一行一条）；**标题行、空行、说明行不算条目，不参与判定**。出现一条非标题、非空、又不以「不许」「必须」开头的行，记「未通过」；一条有效条目都没有也记「未通过」。
4. 以上都过，0.1 才记「通过」。

**0.2 意图的当前版本留过痕。**
1. 用同一算法分别算 `INTENT.md`、`CONSTRAINTS.md` 的当前哈希，两个值都记下来（技能版读法：**SHA-256 整文件原始字节**，[G-09](../../skill/10-规格缺口定论（技能版）.md)；归一化未入规格，插件版须 schema 定死）。
2. 打开最近一条决策记录（§9.1 第 7 步），逐字找这两个值。
3. 有其一出现即「通过」（§15.0 字面为「或」）；两个都没出现，说明意图改过却没留痕，记「未通过」，补一条决策记录后重跑本条。补记录，不要改哈希去凑。

**0.3 这一轮做的契约在缺口里。**
1. 跑 `gaps`（§八）。退出码 0 才继续；退出码 3 记「无法判断」并停。**纯技能版没有 gaps CLI**——按 §八 的语义从材料**现算**缺口清单（**没做过有牙实验的判据与实验无牙的判据**、未验证、孤儿契约与功能、未勾的对齐表，排序按 §17.3 最差在最上），并在判定里写明「现算」与所依据的材料；不许因工具跑不了而跳过本条，也不许把它记成「通过」。
2. 取输出前 3 位的契约标识，与本轮要做的契约比对，命中即「通过」。
3. 没命中，读该契约的 `skipReason`：它是 `contract.json` 的**顶层可选字段**（`skipReason: string`），非空即「通过」，为空记「未通过」（G-03）。
4. 本条只判 `skipReason` 有没有，不判写得好不好（§15.0）。

**0.4 交接时才有这一条。**
1. 先判阶段。阶段 1–5：本条直接「通过」，不读 `HANDOVER.md`——此时交接包还没产生，读它会把第一次 T1 卡死（§15.0 注意 4）。
2. 阶段 6：跑 `handover`（§八），退出码 0 才继续；退出码 3 记「无法判断」。
3. 用 `handover` 返回的六个节名比对 `HANDOVER.md` 的标题，缺一节记「未通过」。
4. 查接收方验收记录：字段存在且非空即「通过」，缺失或为空记「未通过」。本条只判存在性，不判质量。

**收口。** 四条都「通过」才开工。有「未通过」回补材料；有「无法判断」不许开工，也不许把它记成「通过」。

## 出口判据

1. 四条各有明确结论，取值为五个状态之一。**按步骤的停止规则未跑到的条目记「未验证」，不算缺结论**；任何一条不是「通过」（含「未验证」），本卡即不通过。
2. `gaps` 的退出码为 0，或为 3 且 0.3 记「无法判断」。退出码 3 却把 0.3 记成「通过」即失败。
3. 阶段 1–5 时 0.4 记「通过」。若此时因 `HANDOVER.md` 缺失把 0.4 记成「未通过」，即失败——时序搞反了。
4. 抽查 0.1：复制一份 `INTENT.md` 删掉其中一节，重跑 0.1 第 1 步，必须判「未通过」；仍判「通过」即失败，说明这条检查红不了。
5. 抽查 0.3：拿一个不在前 3 位、`skipReason` 为空的契约跑一遍，必须判「未通过」；判「通过」即失败。
6. 开工记录里没有「无法判断」被当成放行的痕迹；一旦出现，整轮结果作废。

## 业界做法参考

| 参考 | 做到哪一步 | 本卡的差异 |
|---|---|---|
| Spec Kit（N1 首选）的 `constitution.md` 与 `spec.md` | 把目标与约束从对话搬进仓库文件，后续命令先读文件再动手 | 本卡不定义模板结构，只判在不在场（0.1）；模板由 [模板-INTENT.md](./模板-INTENT.md)、[模板-CONSTRAINTS.md](./模板-CONSTRAINTS.md) 承载 |
| Spec Kit 的 assess 扩展 `decision.md` | 把「做不做、为什么」写成可查的决策记录 | 0.2 只借它的留痕形态：当前哈希要出现在最近一条决策记录里 |
| Spec Kit 的 `converge`（D1 首选） | 每轮结束反向对照 spec 报收敛，实现不能悄悄变成新目标 | 本卡把检查提到开工前，只比哈希与缺口顺序，不做语义收敛 |
| OpenSpec 的 `changes/<name>/` delta | 只有 delta 写到的需求属于本轮范围 | 用 `gaps` 前 3 位加 `skipReason` 代替 delta 清单，不要求每轮新建目录 |

与 Spec Kit 的差异明显，按 [ADR-015](../../设计/adr/015-说现成做法不适用必须给两个代价.md) 给两个代价，用同一个量（每轮多花的分钟数）比：Spec Kit 的 converge 每轮多一轮核对，约 5 分钟，换来实现漂移当场可发现；本卡每轮只比哈希与缺口顺序，约 1 分钟，代价是「意图字面没变、实现已经偏了」这类漂移本卡完全看不见，只能留到复核阶段才暴露。
