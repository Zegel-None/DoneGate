# 模板-INTENT

`INTENT.md` 的填空模板：四节固定，人填，agent 只读。本卡只管怎么填、按什么顺序填、填成什么样算过；四节各自承载什么规则，出处是 §2.1，本卡不重写。

## 入口条件

- 人要新建或重写仓库里的 `INTENT.md`，或 agent 在本轮真正动手前要把意图读进来。阅读时机、作者归属、压缩策略一律按 §2.1，本卡不复述。
- 动笔前先备齐三样：这件事要解决的具体麻烦、被它影响的具体角色、至少一个**能被外部观察**的成功条件（§2.1 的原话是「能被外部观察」，不限于仓库外——仓库内可观察也算）。三样缺一样就停下，别边填边想。
- 规格 [02-规格.md](../../设计/02-规格.md) 是唯一权威。本卡与规格冲突时以规格为准，并把冲突原文回报给 lead，不要自行折中。

## 步骤

1. 先抄骨架再填内容。四节标题原样照抄，不改字、不换序、不加第五节；**四节之后只许跟一行 `冒烟命令：<单条命令>`**（G-08——它是 T0 档的另一半，是行不是节）：

```markdown
## 为什么做
## 服务谁
## 什么算成功
## 明确不做什么

冒烟命令：node scripts/smoke.mjs
```

2. 按下面这张表逐节填。每行末列就是这一节的验收；本行不成立就停在本节改，别带着缺口往下填。

| 节 | 填什么 | 这一节算过 |
|---|---|---|
| 为什么做 | 一句话，**不含没有比较对象的词**（「更好」「更快」这类）；有比较就说清和什么比 | 把比较对象圈出来；圈不出就是没写。规格没要求给出量 |
| 服务谁 | 具体的人或角色，带上他什么时候会撞上这件事 | 读的人能说出「就是干这个活的某某」；说不出就是没写 |
| 什么算成功 | 至少一条，每条都能拆成 claim / observable / scope（§四） | 拿到 observable 的人自己跑一遍，能判真假 |
| 明确不做什么 | 至少一条，指向具体动作、文件或范围 | 照着这句能指出本轮不许碰的东西 |

3. 拿两个反例对照，命中任一条形状就等于没写：

- **反例一（空转）**：「为什么做」写「把这套流程搬过来，整体会顺很多」。顺是相对什么、顺多少都没给，下一轮的人无法判断做到没有。
- **反例二（无法观察）**：「什么算成功」写「用起来不别扭」。没人能替这句话跑一次并得出真假，它只是一条愿望。

## 出口判据

1. 数 `INTENT.md` 的二级标题：正好四个且与骨架逐字相同。少了、改名了、多出第五节，任一命中即失败。
2. 逐节找实字：出现空节，或整节只有一个占位词（如「待补」「同上」），失败。
3. 把「什么算成功」的每条拆成 claim / observable / scope（§四）：还有拆不出的条目留在文件里，失败。
4. 「明确不做什么」的每条都要能指到具体动作、文件或范围：一条也指不到任何实处的，失败。
5. 请没参与讨论的人按其中一条 observable 实跑一次：跑完既判不出真也判不出假，失败。


## 业界做法参考

| 参考 | 它做到哪一步 | 本卡的差异 |
|---|---|---|
| Spec Kit `spec.md` | 把一句需求展开成带用户场景、需求条目与验收标准的文件 | 本卡只留四节，每节一行量级，不编号场景 |
| Spec Kit `constitution.md` | 项目级原则写在每个功能之前，逐轮先读 | 本卡不承载项目级原则，只写单个对象的意图 |
| Spec Kit assess 的 `decision.md` | 把「做不做、为什么」写成 go / needs-clarification / kill | 本卡不判做不做，只判写没写清 |
| OpenSpec `proposal.md` | 意图随变更归档，累积成可回溯的历史 | 本卡是单文件，不留历史版本 |

差异最大的一处：Spec Kit 用 `[NEEDS CLARIFICATION: …]` 在模板里标出歧义、禁止模型补全；本卡不引入这个标记，改为在出口判据第 2、5 条事后拦。两个代价：

| 方案 | 正确性 | 成本 |
|---|---|---|
| 引入歧义标记 | 歧义在填写当场被挡住 | 每加一个未登记的词都要走一遍统一规范第四节的登记与全卡扫描 |
| 本卡不引入 | 歧义靠事后判据拦，漏网仍会发生 | 漏网条数估不出来，按 [adr/015](../../设计/adr/015-说现成做法不适用必须给两个代价.md) 标 `unquantified` |
